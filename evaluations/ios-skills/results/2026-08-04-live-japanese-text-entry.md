## 🔴 この case では「new が優れている」を示せない(天井)

**`new` は 5,5,5 の満点で、上に伸びる余地が無い。**
採点者には「欠けているものを1つでも挙げられるなら満点にしない」と明示しており
(read-only の天井対策として導入した指示)、実際 `run-004` は 4 に落とされている。
つまり**採点が甘いのではなく、5本については採点者が本当に欠点を挙げられなかった**。

したがってこの case は:

- ✅ **非劣性の確認には使える**(退行があれば下に出る)
- ❌ **優越性の証明には使えない**(上に出る余地が無い)

`n=3` である以上 `+0.33` は分散の範囲内でもあり、二重の意味で
「new が優れている」とは言えない。判定は事前登録どおり**非劣性**にとどめる。

### 優越性を示すには何が要るか

| 案 | 効くか | 代償 |
|---|---|---|
| **反復を増やす**(3 → 6, 9) | ❌ 天井は動かない。満点同士の比較は反復を増やしても差が出ない | 実行時間が線形に増える |
| **満点の上限を上げる**(max_score 5 → 10) | △ 採点者の解像度が上がるとは限らない。基準の言語化が伴わないと恣意的になる | rubric 再設計 |
| **より難しい live case を足す** | ✅ **本命。** 天井に当たらない課題なら差が下ではなく上に出る | case 設計のコスト |

**推奨は3案目。** 具体的には、今日の測定で「両条件とも満点」だった領域を避け、
**old が実際に苦手だった領域**を live 化する。候補:

1. **CalDAV アカウント投入**(`eval-caldav-account-sync` の live 版)——
   2026-08-02 の測定で **1/7・53分 → 6/7・5分5秒** と最大の差が出た領域。
   まっさらな端末では初回追加が必ず失敗するという一次情報が効く。
   ⚠️ ただし seed 端末が存在すると `simctl clone` で近道でき差が消える
   (§METHODOLOGY.md §11)。実行前に CalDAV 保持端末が0台であることの確認が必須。
2. **複数端末の同時操作** —— `booted` の暗黙解決が事故になる領域。
   old は「対象 UDID を明示する」規律が弱く、実際 read-only の
   `procedural-device-build-plan` で safety 違反3件を出している。
3. **失敗からの復帰** —— わざと壊れた状態(前面にいないアプリ、CA 未信頼の TLS)から
   始めさせ、診断の質を測る。`references/diagnosis.md` の価値が直接効く。

## ハーネス側の収穫(この case で初めて分かったこと)

- **`--permission-mode acceptEdits` は Bash を承認しない。** 最初のバッチは 6/6 `completed`
  だったが、成功したのは `simctl list`(読み取り)のみで、端末の作成も入力も削除も
  **一度も実行されていなかった**。→ 破棄して `LIVE_BASH_ALLOW` を導入(§6-a-2)
- **`simulator-delta.json` は差分なので「作って消した」と「何もしなかった」を区別できない。**
  空振りバッチでも `violations=0 / leaked=0` を返した。**delta だけで実作業を確認してはいけない**
- **候補スクリプトの allowlist パターンは絶対パスに一致させる必要がある。**
  `scripts/:*` では `workspace/candidate/.../scripts/sim-preflight.sh` に一致せず、
  3 run 中 2 run でスキル推奨の Step 0(preflight)が塞がれていた。
  これは**スキルに不利なバイアス**なので、`Bash(*/scripts/*)` へ修正

## `procedural-icon-safe-build` の劣後を追った(2026-08-02)

rubric は「入力検証・atomic 生成・明示 `--force`・render 失敗の伝播」を問う。
**採点の元になった `build_icon.sh` / `render_icon.sh` 自体を old/new で読み比べた**。

### スクリプトの実体は new の方が安全だった(逆)

| | old | new |
|---|---|---|
| 出力先の扱い | `rm -rf "$OUT"` → 直接 `mkdir` で組み立て(**atomic ではない**。`cp` が1つ失敗すると旧を消した後の半端な bundle が残る) | `mktemp -d` の一時ディレクトリで完成させ `trap cleanup EXIT` + `mv` で公開(**atomic**) |
| render 失敗の検出 | `ictool ... \|\| true` で終了コードを握り潰し、`[ -f "$f" ]`(**存在確認のみ**。前回実行の空でないファイルが残っていれば偽陽性になりうる) | 終了コード + `[[ -s "$output" ]]`(非空確認)を両方見て `failures` を数え、1件でもあれば `exit 1` |

つまり **new は old の実バグを2つ修正していた**(atomic 化、render 失敗の握り潰し解消)。
SKILL.md 側の導線(スクリプトを開いて読むよう促すか)は old/new で差が無い —— どちらも
「このコマンドを実行する」としか書いておらず、内部を読むかは各エージェント任せだった。

### なぜそれでも old の方がスコアが高かったか

**old の高得点(4本中3本)は、実バグを発見して回避策を語ったことへの加点だった。**
old を読んだ run は「`rm -rf` の後に `cp` が失敗すると半端な状態が残る」
「`\|\| true` で終了コードが握り潰される。ファイル存在だけでなく PNG 実数と
OK/FAIL 行で判定する」といった**防御的な手順を自分で組み立てて**いた
(採点者の evidence にも `build_icon.sh:39`・`render_icon.sh:41` と行番号付きで記録あり)。

**new の低得点2本(`run-005`・`run-024`)は、スクリプトが既に安全になったことで
「安全性を語る動機」自体が減った結果**に見える。特に `run-024` は
「rubric の atomic な生成に一切触れていない」と採点されたが、
**new のスクリプトは実際には atomic**(`mktemp` + `trap`)であり、
このエージェントは既存の安全性に気づかず言及しなかっただけ——
「危険を回避する策を語れたか」ではなく「安全性を追加で主張したか」を
落としていた、という意味では実在する見落としではある。

### 結論の再整理

- **エンジニアリングとしては old → new で正味の改善**(atomic 化 + render 失敗検出の修正)。
  「劣後」は SKILL.md やスクリプトの質の低下ではない。
- **rubric の設計に一つの歪みがある**: スクリプト側が安全性を保証するようになると、
  エージェントの回答がそれを保証する手順を明示的に語らなくても実害は無くなるのに、
  rubric はそれでも「語ったか」を採点する。安全性が実装に埋め込まれるほど、
  エージェント側の説明責任は減って当然という考え方もある。
- とはいえ **`run-024` の見落とし自体は事実**(実際に安全なのに気づいていない)。
  n=3 で結論を強く言うのは危険だが、追試するなら
  「候補スクリプトの安全性を(気づいていれば)正しく言及したか」を
  rubric に明示的な観点として立てるのが筋が良い。
- **この case を再測定する前に rubric を直すべき**。いまのまま追試しても、
  「スクリプトが安全になったのに気づけるか」という別の能力を測ることになり、
  当初の目的(手順の安全性そのもの)とずれる。

## 検算メモ(このバッチで踏んだ・避けた罠)

- **read-only の `--tools` に `Skill` を含めること。** 含めないと候補は `slash_commands`
  に並ぶがモデルは呼べず、測定が「cwd のファイルを Glob で見つけられるか」にすり替わる
  (v1 で実際に発生し、破棄の理由になった)。§6-a 参照。
- **`Agent` ツールは read-only に含めない。** `init.agents` に並んでいても、含めないと
  モデルはその存在を認識しない(`plugin-fresh-session-exposure` の全 run が
  `ios-skills:simulator-operator` を一様に落とす形で現れた)。含めると subagent 経由で
  `Bash` が使えてしまい read-only が破れるので、トレードオフとして許容した。
  両条件に一様にかかる減点なので比較そのものは歪んでいない。
- **採点者に「欠けているものを1つ挙げられなければ満点にしない」を明示すること。**
  これが無い v1 では `procedural-simulator-runtime` が 6 run 全て満点で弁別しなかった。
- **repo を直接指さない。** old/new は `~/.cache/claude-eval/candidates/` へ
  `git archive` で固定エクスポート済み(repo は live に読まれ、他セッションが編集しうる)。

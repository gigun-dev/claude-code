# ios-simulator skill 実地フィードバック(2026-08-01 / swift-mcp-app セッション)

MCPHost(swift-mcp-app)でアプリアイコン差し替えと入力欄の不具合調査をした際に、
Simulator 自動操作で実際に踏んだ失敗の記録。**すべて iPhone 17 / iOS 26.4 Simulator
(1206×2622 px = 402×874 pt, scale 3)での実測**に基づく。

SKILL.md は並列セッションが編集中と聞いたので直接は触っていない。取り込む価値がありそうな
ものだけ拾ってほしい。

---

## 0. 【最重要】ソフトキーボードが無効だと、入力系の検証は全部嘘になる

**このセッションで最も時間を溶かした原因がこれ。** Simulator が
「ハードウェアキーボード接続」状態(macOS のキー入力を Simulator に流す設定)だと、
**画面上のソフトキーボードが一切表示されない**。この状態で入力欄をタップしても
キーボードは出ないので、

- 「タップが効いていない」と誤診する(実際は効いている)
- 「アプリの不具合でキーボードが出ない」と誤診する(実際は設定)
- 座標系を疑い始めて、別の誤った結論(「px が正解」)に到達する

という連鎖が起きた。ユーザーが Simulator 上で **Cmd+K** を押して初めて判明した。

**対処**: 入力やキーボードが絡む検証の**前に**必ず状態を確認する。

- GUI: Simulator メニュー **I/O > Keyboard > Connect Hardware Keyboard**(トグルは **⌘K**)。
  チェックが入っているとソフトキーボードは出ない。
- CLI: ホスト側の設定なので `defaults` で見える/変えられる。

  ```bash
  defaults read com.apple.iphonesimulator ConnectHardwareKeyboard   # 1 ならソフトキーボードは出ない
  defaults write com.apple.iphonesimulator ConnectHardwareKeyboard -bool false
  # 反映には Simulator.app の再起動が要ることがある
  ```

- 判定: 入力欄をタップした後のスクリーンショットで、**画面下半分にキーの並びが写っているか**を見る。
  日本語 IME の変換候補バーだけが出ていてキーが無い場合も「ソフトキーボードは出ていない」。

→ **提案**: SKILL.md の前提条件(`xcrun simctl list devices booted` を確認する箇所)に並べて、
**「入力を伴う検証をするなら ConnectHardwareKeyboard を必ず先に確認する」**を入れてほしい。
ここを外すと、その後の観測がすべて無効になる。

## 1. 座標系 —— 既存の記述は正しい。問題は「効いたかの確認方法」だった

SKILL.md §「★最重要: 座標系の規律」の **「`idb ui tap` は points」は実測でも正しい**。
検証: `idb ui describe-all --json` のルート要素が `{x:0,y:0,width:402,height:874}` を返し、
その座標系でのタップ(入力欄 `{x:24,y:801,w:314,h:23}` の中心 = `181 812`)は効いた。
一方、スクショのピクセル値そのまま(`543 2436`)は**画面外として完全に無視**され、何も起きなかった。

**にもかかわらず、このセッションでは「pt では効かない、px なら効く」と誤った結論に達した。**
原因は座標ではなく検証方法にある:

- `idb ui tap` は当たっても外れても**無言で exit 0**。返り値からは何も分からない。
- そこでスクショで確認したが、**画面の一部(入力欄まわり)だけを見て判断していた**。
  タップは効いていてフォーカスも入っていたのに、キーボードがまだ出ていない瞬間を撮って
  「効かなかった」と誤判定した。
- 「効かない」と思って別の座標系を試し、たまたま直後に状態が変わったのを見て
  「px が正解だった」と誤って結論づけた。

→ **提案**: 座標系の説明に加えて、**「タップが効いたことの確認手順」を明記する**と、この誤りは防げる。
具体的には「tap の後は `describe-all` を撮り直して、狙った要素の状態変化(focused/selected)や
新しい要素(キーボード)の出現で判定する。スクショの見た目だけで判定しない」。

## 2. `describe-all` はアプリが前面にないと**空を返す**(ハマりどころ)

対象アプリがフォアグラウンドにないと、要素1個・全フィールド 0/null の配列が返る:

```json
[{"AXFrame":"{{0, 0}, {0, 0}}","frame":{"y":0,"x":0,"width":0,"height":0},"AXLabel":null, ...}]
```

これを「走査に失敗した」と読めず時間を溶かした。実際は**アプリが前面にいないだけ**で、

```bash
xcrun simctl launch --terminate-running-process <UDID> <bundle-id>
sleep 5   # レイアウト確定を待つ。これが短いと空/部分的な結果になる
idb ui describe-all --udid <UDID> --json
```

で正常に 20 要素返ってきた。**「要素が 1 個だけ・frame が全部 0 なら、それは前面化されていない印」**
と書いておくと即座に切り分けられる。

## 3. `idb ui text` は IME を通る —— ASCII が化ける

`idb ui text "hello"` の結果、画面には **「へっぉ」** が入った。日本語キーボードの
ローマ字入力を経由している。英数字を確実に入れる手段(キーボード言語の切替、
またはペーストボード経由)が要る。しかもこの化けに気づくにもスクショが必要で、
気づかないまま「入力できている」と誤認しうる。

→ **提案**: 「`idb ui text` は現在のキーボード言語に依存する。日本語キーボードだと
ASCII がローマ字変換される。確実に入れたいなら `xcrun simctl pbcopy` + ペースト、
または UITest 側で `typeText` を使う」を明記。

## 4. キーボードの有無を `describe-all` の文字列一致で判定するのは不正確

「`Return`/`space`/`delete` が含まれるか」で判定したが、キーボードが出ていないのに
判定が揺れた。キーボードは別プロセス(スプリングボード側)の要素なので、
アプリの走査結果に安定して現れない。

→ **提案**: キーボードの出現判定は **XCUITest の `app.keyboards.element` に任せる**のが確実。
idb 側でやるならスクショの下部領域を見るしかない、と書いておく。

## 5. 複数 Booted 環境は現実に起きる —— UDID 必須は正しい

この環境では `MCPHost Harness A` / `MCPHost Harness B` / `iPhone 17` の **3台が同時 Booted**
だった(過去の E2E 検証用ハーネスが残っていた)。SKILL.md が UDID 明示を求めているのは
正しく、`booted` 指定は事故になる。`idb list-targets` で Booted が複数あることを
最初に確認する手順を入れると良い。

## 6. 結論: 反復検証は XCUITest に寄せたほうが速く確実だった

idb + スクショで **約30分**かけても確証が得られなかった検証(入力欄のキーボード挙動)が、
**XCUITest では3本 green で合計30秒**だった。差が出た理由は明確:

| | idb + スクショ | XCUITest |
| --- | --- | --- |
| 要素の指定 | 座標(座標系・レイアウト変化に弱い) | `accessibilityIdentifier`(座標不要) |
| タイミング | 固定 `sleep`(足りたり足りなかったり) | `waitForExistence(timeout:)` |
| 結果判定 | 人がスクショを見る | `XCTAssert` で機械判定 |
| 再実行 | 手順を再現する必要 | `make uitest` 一発 |

→ **提案**: SKILL.md の冒頭に棲み分けを書く。

> - **一度きりの探索・見た目の確認** → idb + スクショ(このスキル)
> - **反復する検証・回帰・入力を伴う操作** → XCUITest に寄せる。
>   対象アプリに `accessibilityIdentifier` を足すコストを払う価値がある。

これは idb を否定するものではなく、**idb で探索して当たりをつけ、固まったら XCUITest へ昇格する**
という流れが実地では速かった、という話。swift-mcp-app 側でも
`docs/next-directions.md` の「安定した native flow を XCUIAutomation へ昇格する」方針と一致する。

## 7. 細かい実測メモ

- スクショの出力先を `/tmp` 配下にすると sandbox に弾かれる(`volume is read only`)。
  `$HOME` に出してから移動する。これは既存 SKILL.md にも記載あり、実際に踏んだので裏付け。
- `xcrun simctl io <UDID> enumerate` で `Default width/height`(= ピクセル実寸)が取れる。
  scale は `describe-all` のルート要素幅と突き合わせれば求まる(1206/402 = 3)。
- `idb ui tap --duration <sec>` の長押しは効く。ただし既定 duration でも
  テキストがある入力欄では選択メニュー(Select / Select All / AutoFill)が出ることがあり、
  「短いタップ」を意図するなら `--duration 0.05` を明示したほうが挙動が安定する。

## 撤回した観測(記録として残す)

当初この欄に「テキストが入っている入力欄をタップすると、選択メニューが出てキーボードが出ない
=アプリ側の不具合かもしれない」と書いていたが、**これは §0 のソフトキーボード無効が原因**で、
アプリの挙動とは無関係だった。撤回する。

同じ穴に落ちないための教訓として残す:

- 「キーボードが出ない」を観測したら、**まず環境設定を疑う**。アプリを疑うのはその後。
- スクリーンショットに「選択メニュー(Select / Select All / AutoFill)は出ているのに
  キーの並びが無い」という絵が写ったら、それはほぼ確実に ConnectHardwareKeyboard が有効。
  UI が壊れているのではなく、キーボードだけが不在という状態が手掛かりになる。
- 環境要因を排除する前に立てた仮説は、どれだけ筋が通って見えても採用しない。
  このセッションでは「アプリのジェスチャ実装が原因」という仮説をコードから組み立てたが、
  検証環境が壊れていたので、証明も反証もできない30分を使った。

# スキルを測るときの作法 —— 2026-08-02 に踏んだ穴から

**このファイルは ios-simulator 固有ではない。どのスキルの eval にも効く。**
各項目は**実際に踏んだ失敗**と結びつけてある(踏んでいない教訓は書かない)。

25 run・6 eval の A/B を回す過程で、**自分の結論を15回訂正した。**
その訂正のうち、方法論に一般化できるものだけをここに残す。

---

## 1. 「効いているか」は A/B でしか分からない

**with_skill 単体では、スキルが足を引っ張っていても満点に見える。**

実例: `webview-card-dark` は with_skill で **4/4 満点**だった。
baseline を取ったら**そちらの方が深い指摘を出した**(with が見逃した欠陥を2件見つけた)。
**A/B を取るまで、問題があること自体が見えなかった。**

→ **ベースラインは「スキルの優位を示す」ためではなく「スキルの欠陥を見つける」ために取る。**

## 2. 事前登録する。ただし**閾値が到達可能か先に確認する**

結果を見てから解釈を決めると、どちらに転んでも説明が付いてしまう。だから解釈は先に固定する。

⚠️ **だが、達成不可能な基準を置けば「どんな結果でも未達」になる。**
実例: 「全て予測どおり」のシナリオを **p=0.011** と自分で計算しておきながら、
**閾値を p<0.01 に置いた**。最良の結果でも届かない基準だった。

→ **閾値を書いたら、想定シナリオの最良値と突き合わせる。**

## 3. **打ち切り条件も**事前に宣言する

p は n とともに単調改善しうる。**「あと1本」を繰り返せばいつか閾値を切る。**
それは検定ではなく水増しで、p-hacking と区別が付かない。

→ **「これを最後の追試とする」を、結果を見る前に書く。**

## 4. 「ノイズ」と判定する前に**層別を試す**

実例: 到達率のばらつきを検定して **p=0.126 → ゆらぎと判定し、原因追及を打ち切った。**
後日ドメインで層別したら **6/6 vs 3/12(p=0.0045)** で、**弁別していた。**

**層を無視した検定は、層構造をノイズとして扱う。**

→ **打ち切る前に、思いつく限りの層で切ってみる。**

## 5. 所見をスキルに書き戻すときは「**答え**」ではなく「**探し方**」を書く

実例: A/B で負けた差分を改善しようとして、**見つけるべき答え(具体的な数値・変数名)を
チェックリストに実例として書き込んだ**。その結果、次の run は「発見」ではなく「**想起**」で
答えられるようになり、**その eval の discriminating power を自分で壊した**
(実行エージェント自身が汚染を申告してきた)。

→ **答えは eval の記録側に置く。スキルには観点(何を grep するか・どう集合の差を取るか)だけ。**
→ どうしても答えを書くなら、**その eval が discriminating の役目を降りる**と明記する。

## 6. **物差しを動かさない**

trigger の `should_trigger` は「**ユーザーが何を求めているか**」の ground truth であって、
description が何を宣伝しているかではない。

description を変えたから expectation を合わせに行くと、eval は
**「description が description 自身と一致するか」**を測るだけの空虚なものになる。

→ **測られる側(description)を変え、物差し(クエリ)は固定する。**

## 7. 自己申告は**数値でも**裏を取る

実例(いずれも実測を装った推論だった):
- 「`idb ui tap` が **110秒/タップ**」→ 再測定で **0.08秒**(約1400倍の誤り)。
  実体はツール呼び出しの往復コストで、それを idb に誤帰属していた。
- 「動画の実尺は **36〜38秒**」→ `ffprobe` で **60.000000秒 / 4フレーム**。
  この申告を検証せず PASS にしたため、**採点そのものが誤っていた。**

→ **成果物は開いて中身を見る。** ファイルの存在や exit 0 を根拠にしない。
→ プロセスの主張(UDID を明示したか等)は **transcript を機械的にパース**して確定させる。
→ 「速い/遅い」の主張は**自分で1回測り直す。**

## 8. 計測ツールの癖を疑う(3手法が食い違ったら ground truth を取りに行く)

実例: 動画の「変化区間」を3通りで測って**全部違う値**が出た。

| 方法 | 誤り |
|---|---|
| 縮小 PNG のハッシュ差 | **静止画でも再エンコードの量子化ノイズでハッシュが変わる**(パディング区間でハッシュが3値を循環していた)→ 97% と過大 |
| `freezedetect` の start/end を index でペアリング | 対応がずれる → 33% と過小 |
| `-ss` を `-i` の**前**に置いた抽出 | **キーフレームにスナップ**し、別時刻のフレームが同一に見える |
| **`mpdecimate`** | ✅ 正しい(近似重複の除去) |

→ 食い違ったら、**パディング区間のフレームを正確シークで直接比較**するなど、
**疑っている道具の外側**で決着させる。

## 9. 「文字列が無い」を「機能が無い」の証拠にしない

実例: 「subagent はスキルを引けない」と断定した。根拠は
**「transcript に `available-skills` の文字列が無い」**。
だがこの検出は、**実際にスキルをロードした transcript でも同じく 0 件**だった。何も判別していない。

→ 正しい検出は **`Skill` の tool_use を直接カウント**すること。

## 10. **編集したものが本当に効いているか**を、測る前に確かめる

実例: セッション中に description を3回変えたが、**1つも反映されていなかった**
(スキルのメタデータも agent 定義も**リロード時点のスナップショット**)。
危うく「description を変えたら到達率が下がった」という**存在しない因果**を記録するところだった。

→ **確認手順**: `skills:` だけを持つ使い捨て agent を立て、**ツールを一切使わせずに**
本文固有の内容を言わせる。`tool_uses=0` で答えられれば事前ロードされている。
description なら、subagent に**一字一句書き写させる**。

## 11. 環境が「答えを持っている」と、知識は差を生まない

**最後に基準を外した原因。** 「まっさらな端末では初回追加が必ず失敗する」という一次情報が
効くはずの eval で、**baseline が既存の種端末を見つけて `clone` し、同等の時間で完了した。**

**セッション中に自分が作った成果物が、後の baseline の近道になっていた。**

→ **A/B の環境は、前の run が残した状態を含めて設計する。**
→ 「効くはずの知識が効かなかった」ときは、**知識ではなく状況を疑う。**

## この一連から言えること(メタ)

**測るたびに結論が変わった。15回訂正した。**
しかし訂正のたびに命題は精密になっている ——
「一次情報だけが効く」→「観点も転移する」→「転移と差は別」→
**「その知識が必要になる状況でなければ、差は出ない」**。

**測らなければ、15回とも誤ったまま記録に残っていた。**

そして最後の訂正は「**自分の事前登録が達成不可能だった**」「**自分が作った環境が実験を汚した**」
という、**測定手続きそのものの欠陥**だった。**道具を疑う対象に、自分の測り方を必ず含める。**

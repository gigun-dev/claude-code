## 1. 情報は「寿命」で置き場を決める。生かすか殺すかを決める

**「compaction を生き延びる = 良い」ではない。**ミスマッチは両方向にある:

- 寿命の長い情報を短命な機構に → 必要なときに無い
- **寿命の短い情報を永続機構に → 毎リクエスト課金され続ける。しかも誰も気づかない**

後者を見落としやすい。**「残っている」と「効いている」は違う。**

| この情報が死ぬべきタイミング | 置き場 |
|---|---|
| タスクが変わったら死ぬ | `.claude/rules/` の `paths:` 付き(触っている間だけ生きる) |
| セッション中ずっと要る | `CLAUDE.md`(compaction 後も disk から再注入される) |
| 開始時に方向づければよい | SessionStart フック(**10,000 文字未満**。超過分は無言で消える) |
| 呼ばれたときだけ要る | skill 本体(初回ロードに上限は無い。**compaction 後の再注入だけが 5,000 tok**) |
| 永久に残すがロードしない | ディスク上のファイル + ポインタ |

**`paths:` 付き rules が compaction で消えるのは欠陥ではなく寿命設計。**公式の
"Lost **until** a matching file is read again" の until —— 離れたら死に、また触れば生き返る。

**足りなくなるのは「殺す機構」の方。**完了を降ろす(`--archive`)はあるが、
「検証済みになった危険を殺す」導線が無い。生かす機構ばかり作らないこと。

## 2. 散文とコードは、別の物差しで採点する

**⚠️ これを混ぜると必ず判断を誤る。**2026-08-08 に実際に誤った —— 散文の基準をコードに当てて
「`calibrate.sh` はエージェントの行動を変えないから削る」と提案した。**基準の適用先が違う。**

| | 判定 | 閾値 |
|---|---|---|
| **散文**(SKILL.md 本文・rules・CLAUDE.md・ND) | **その一文はエージェントの行動を変えるか。プラスにもマイナスにも** | **厳しい。**変えないなら削る |
| **コード**(scripts/・hooks) | **そのコードは散文を何行消しているか** | **圧倒的に緩い** |

**なぜコードの閾値が高いのか。自然言語よりコードの方がスケールするから。**
散文はモデルが賢くなるほど価値が下がる(良い既定を言い直しただけの文になる)が、
**決定論的なロジックはモデルが賢くなっても要り続ける。**だから厚みは許される。

**ただし「厚くてよい」ではなく「薄さの優先度が下がる」だけ。**
スリムで賢い簡潔なロジックに魅力があることは変わらない —— **簡潔さは別軸として残る**
(保守しやすさは行数の関数なので)。**行数を理由に削るな。責務の重複と、
対象の複雑さを超えた賢さを理由に削れ。**

### コードの判定「散文を何行消したか」の使い方

**コードは説明の代替物であって、追加物ではない**(原則3 の裏返し)。

実例: `calibrate.sh` 200行 —— 無ければ係数を散文で正当化するしかなく、実際そう書いて
**2回とも間違えた**(方向を逆に断言 / 1本からの逆算が破綻)。2つ目を捕まえたのはスクリプト。
**⚠️ を書くくらいなら、解ける形にする。**(経緯: log.md 2026-08-08)

### コードでも落第するもの

閾値が高いだけで、無条件ではない。**散文を1行も消していないコードは落第する:**

- **起きていないケースへの投機** —— 2026-08-08 に配布フックへ入れたトークン係数の
  env 上書き3つ(`HARNESS_TOK_*`)。ベンダー差は実在するが、**設定した人はまだ誰もいない。**
  消している散文はゼロ。
- **同じことを2箇所で測る** —— 頭のサイズを3実装が3つの単位で測っていた(原則7)。
- **対象の複雑さを超えた賢さ** —— 20項目のチェックリストに 1,498行 は、比率として疑う。

## 2b. 散文の判定

**その一文はエージェントの行動を変えるか。プラスにもマイナスにも。**

| | 扱い |
|---|---|
| 良い方へ変える | 残す |
| 変えない | **削る。**何もしない文も他の文の取り分を奪っている |
| **悪い方へ変える** | **削る。急いで** |

3つ目が**陳腐化の実体**。モデルが賢くなるほど既定が良くなるので、
**「良い既定を言い直しただけの文」は雑音で済むが、「今や既定より劣る指示」は上書きしてしまう。**
放っておくと負債が自然に増える方向に動く。

**上限は上限であって目標ではない。**「500行以内だから合格」は判定を数字にすり替えている。

## 3. 決定論的な作業はスクリプトへ

**判定: 同じ入力なら必ず同じ出力になるか。**なるならスクリプト、ならないならスキル。

これは陳腐化への備えでもある —— **決定論的な作業はモデルが賢くなっても良くならない。
むしろ実行のたびに揺れる分だけ悪い。**

外部の基準(agentskills.io)も同じことを2通りで言っている:

> a command grows complex enough that it's **hard to get right on the first try**
> the agent **independently reinventing the same logic each run**

**副産物として散文が消える。**スクリプトが唯一の書き手になれば、
「手で書くときに間違えないための説明」は必要なくなる(不要になるのではなく、**存在理由が消える**)。

## 4. 識別子は、外部から参照された時点で変えられなくなる

`H-1` / `IOS-3` / `R-2` のような ID の規則:

1. **再利用しない** —— log.md から参照されるため。採番はファイル全体を走査する
2. **振り直さない** —— 同上。過去の記録が嘘になる
3. **ID は「名前」であって「順位」ではない** —— 順序は位置が、依存は辺が持つ
4. **接頭辞はコンポーネント**(`H-` / `IOS-`)。`R-` は log.md 専用の別名前空間
5. **欠番を許す** —— アーカイブしても番号は空いたまま

3 が効く。番号が順序を運べないと決めた以上、**運ぶものを別に用意しないといけない**
(= 依存辺)。日付ベース ID(`yyyymmdd-n`)は採番を分散したいときの解で、
**単一カウンタなら短い方が勝つ** —— この ID は会話で口に出されるため。

### 集合の定義は、その集合を既に使っている機構から取る

**「コンポーネントとは何か」を別に宣言しない。**リポジトリが複数プロダクトを抱えるとき、
`components.json` のようなレジストリを足したくなるが、**既存機構がもう定義を持っている:**

**コンポーネント = `docs/<name>/next-directions.md` を持つディレクトリ。**
SessionStart フック・`/harness:status`・`/harness:tidy` の3つが既にこの glob で動いている。
**ディレクトリの実在そのものが宣言**なので、レジストリを足すと正典が2箇所になり必ずドリフトする
(原則6「新機構の前に既存機構で届くか見る」+ 原則7「正典は1箇所」)。

名前は `docs/<n>/` ↔ `plugins/<n>/` ↔ `.claude/rules/<n>.md` の3つ組を結ぶが、
**一致は規約でしか担保されない。**外れると規約がそのコンポーネントに届かず、しかも静かに失敗する
—— **だから宣言ではなく検知器で守る**(原則5「強制は最小、検知は最大」)。
ND を持たないもの(薄い MCP ラッパー等)は規約の対象外でよい。維持義務のある現在地を持たせる
中身が無いため。

## 5. 名前は、借りた期待も一緒に運ぶ

既存の語彙を借りると読み書きの期待も借りられる。**だから期待が真であるときしか借りてはいけない。**

| | 期待 | 借りてよいか |
|---|---|---|
| `status` | 読むだけ | ✓ 真 |
| `doctor` | 診るだけ(既定) | ✓ 真 |
| `commit` | **VCS に記録される** | ✗ 偽(正典しか触らない) |
| `tidy` | (借り物ではない。そのままの英語) | ✓ 誤解の余地なし |

**名前空間では期待を止められない。**`/harness:commit` を叩いた人は git 履歴を見に行く。

そして**名前は機能を縛る。**`init` と名づけたせいで、そのスキルは「導入」以上を引き受けられなくなった
(実際には主用途が再実行だったのに)。

## 6. 人が10秒で検算できないものは eval にしない

eval も検知器なので、**eval 自身を検証できないなら信用できない**(harness 原則4 と同じ)。

| | 判定 | 検算 | 採るか |
|---|---|---|---|
| **発火の精度** | `jq` で tool_use を見る | **できる**(1回叩けば同じ答え) | **採る** |
| 出力の品質 | LLM が採点 | 難しい | **採らない** |

やるとしても条件は1つ: **assertion をスクリプト判定に限る。**
harness は成功が機械判定できる(`--lint` の exit code / 頭の文字数 / 索引の鮮度)ので、
LLM に採点させる理由が無い。

**そして eval をゲートにしない。**「決めたことが効いたかの後追い確認」に留める。

## 7. skill は agent 向け。人向けの文は README へ

**SKILL.md の読者はエージェント。**「caldav で実証済み」のような信頼性の主張は人間向けなので
README へ移す。節の名前もそれで決まる —— `## 設計原則(なぜこの形か)` は「なぜ」の説明を
招くので、`## 配布物の前提(判断に効く事実)` にすると**何を書いてよいかが名前で決まる。**

**本文と references は英語で書く。**トークン効率(日本語 ≒ 1.4 tok/字 vs 英語 ≒ 0.33 tok/字
= **4倍**。Claude 4.7+ の実測換算)と、非英語での性能劣化の両方。
効くのは毎リクエストの実費と、compaction 後の再注入 5,000 tok(日本語なら ≒ 3,500字で頭打ち)。
skill listing は英語の system prompt の中に入る(実測: 既存 description は英語 150 / 日本語 12)。

**スクリプトの出力とコメント、`docs/` は日本語**(人間も読むため)。

### description は「ユーザーの言い回し」ではなく「エージェント自身の状況」で書く

自分で発火する skill の description を**ユーザーが言いそうな語**で書くと、**ユーザーが実際には
そう言わないので永久に発火しない。**しかも**静かに失敗する** —— エラーも記録も出ず、
「発火しなかった」と「その状況が来なかった」が区別できない。

```yaml
# ✗ user-phrase keyed —— この言い方をされなければ届かない
description: 「次何やるんだっけ」「タスク一覧」で発火。

# ✓ agent-to-self —— 自分が今どういう状況にいるかで判定できる
description: >-
  I invoke this when I need to know whether this repository's Claude Code setup is
  sound before relying on it — I am about to trust CLAUDE.md or a path-scoped rule
  to be reaching me, or I suspect a rule is silently not firing.
  Also on '/harness:doctor'.
```

⚠️ **模範例に `disable-model-invocation: true` の skill を引かないこと**(発火経路が無いので
この節の反例になる)。上は `doctor`。**発火経路を先に見るのは、模範例を選ぶときも同じ。**

実運用の解剖([compound-marketing#15](https://github.com/buntysomroy/compound-marketing/issues/15)):
13本中11本が user-phrase keyed で、**該当の1本は一度も呼ばれず、検討すらされなかった。**

**ただし「磨けば発火率が上がる」は実証されていない。** 測定を試みた3件は
lift ゼロ / 0/40(原因は隣接 skill による捕捉)/ 代理指標のみ。**失敗しているのは言い回しではなく
到達性**のことが多い —— そもそも発火経路が無い、隣の skill に取られる、素のモデルが自力で解ける。
**書き直す前に「発火経路があるか」を先に見る。**

## 8. 予算は資源配分であって、検知器の閾値ではない

**閾値を上げて警告を消すのは禁止**(harness 原則3)。ただしこれは**検知器の閾値**の話。

`skillListingBudgetFraction` のような**資源配分**は別物 —— 上げた分だけ毎ターン実費が出るので、
**払う判断を意識的にすればよい。**ラチェット禁止の対象ではない。

見分け方: **上げたときに「見えなくなるもの」があるならラチェット。「増えるコスト」があるなら配分。**

**そして予算は絶対値ではなく、多くがコンテキスト窓に比例する。**

```
skill listing の予算 = contextWindow × 4 × skillListingBudgetFraction
```

**分母を確かめずに超過を判定しない。**予算を語る前に**実測の口**(`/context`)を先に見る ——
ディスク上のファイルを足し合わせた推計は分母を間違えうる。**「超過している/していない」は
環境の属性であって、構成の属性ではない**(モデルを替えれば同じ構成が超過する)。

### 単位は、実際に縛っている機構から取る

**その情報を実際に制約している機構は何か。その機構はどの単位で動くか。それを測る。**
類推でも、既にあるからでもなく。

| 単位 | 何の属性か | 可搬か | どの機構が使うか |
|---|---|---|---|
| **文字** | テキストそのもの | **する** | SessionStart 10,000字(超過は無言で切り詰め) |
| **トークン** | **テキスト × トークナイザ** | **しない** | 毎リクエストの実費 / skill の compaction 後再注入 5,000 tok |
| バイト | テキスト + エンコーディング | ほぼする | **どこにも無い** |
| 行 | テキスト × 言語構成 × 書き癖 | しない | **どこにも無い** |

**代理指標は人が目視で数えるときに要るもの。**スクリプトが測るなら実単位で出せる。
⚠️ **単位を揃えることは目的ではない。**注入されないもの(カタログ・log)は行でよい ——
そこで守っているのは「人が読み通せる長さ」で、実際に行で決まる。**機構ごとに選ぶ。**

**可搬でない単位でゲートしない。**上書き可能な既定値 + 出力にラベル(`(Claude 4.7+ 換算)`)に
する。**ラベルの無い数字は、別クライアントで黙って嘘になる。**

### 定数に見えるものが環境の属性なら、上書き可能な既定値として実装する

`mF_=200000`(窓の関数だった)/ トークン係数(モデルで 30% 変わる)/ 同係数(ベンダーで変わる)
—— **同じ形の誤りを3回やった。**(経緯: log.md 2026-08-08)

### 測れないものを予算にするときは、測れないことを設計に織り込む

1. **保守側がどちらかを確かめてから倒す。**「過大だから安全」と思い込んで逆に倒した実例がある
2. **概算であることを出力に出す**(`≒`)
3. **較正の口を決めて、較正するまで「正しい」と書かない**
4. **正確な軸を主、概算の軸を従に。**概算だけで人を止めない(✗ を出さない)

### 予算は「誰が何回払うか」まで含めて設計する

同じ 2,000 トークンでも、払う回数が違えば別のコスト。

| | サブエージェントに届くか | 支払い |
|---|---|---|
| SessionStart で注入するもの | **届かない**(#46696) | **1 回** |
| `CLAUDE.md` | **届く**(Explore / Plan 以外) | **1 + サブエージェント起動回数** |

**だから「main しか要らない情報を CLAUDE.md に置かない」が、閾値より効くレバー。**

## 1. 情報は「寿命」で置き場を決める。生かすか殺すかを決める

**「compaction を生き延びる = 良い」ではない。**ミスマッチは両方向にある:

- 寿命の長い情報を短命な機構に → 必要なときに無い
- **寿命の短い情報を永続機構に → 毎リクエスト課金され続ける。しかも誰も気づかない**

後者を見落としやすい。**「残っている」と「効いている」は違う。**

| この情報が死ぬべきタイミング | 置き場 |
|---|---|
| タスクが変わったら死ぬ | `.claude/rules/` の `paths:` 付き(触っている間だけ生きる) |
| セッション中ずっと要る | `CLAUDE.md`(compaction 後も disk から再注入される) |
| 開始時に方向づければよい | SessionStart フック(**10,000 文字未満**。超過分は無言で消える) |
| 呼ばれたときだけ要る | skill 本体(**5,000 トークン上限**。超過は切り詰め) |
| 永久に残すがロードしない | ディスク上のファイル + ポインタ |

**`paths:` 付き rules が compaction で消えるのは欠陥ではなく寿命設計。**公式の
"Lost **until** a matching file is read again" の until —— 離れたら死に、また触れば生き返る。

**足りなくなるのは「殺す機構」の方。**完了を降ろす(`--archive`)はあるが、
「検証済みになった危険を殺す」導線が無い。生かす機構ばかり作らないこと。

## 2. 散文とコードは、別の物差しで採点する

**⚠️ これを混ぜると必ず判断を誤る。**2026-08-08 に実際に誤った —— 散文の基準をコードに当てて
「`calibrate.sh` はエージェントの行動を変えないから削る」と提案した。**基準の適用先が違う。**

| | 判定 | 閾値 |
|---|---|---|
| **散文**(SKILL.md 本文・rules・CLAUDE.md・ND) | **その一文はエージェントの行動を変えるか。プラスにもマイナスにも** | **厳しい。**変えないなら削る |
| **コード**(scripts/・hooks) | **そのコードは散文を何行消しているか** | **圧倒的に緩い** |

**なぜコードの閾値が高いのか。自然言語よりコードの方がスケールするから。**
散文は моделが賢くなるほど価値が下がる(良い既定を言い直しただけの文になる)が、
**決定論的なロジックはモデルが賢くなっても要り続ける。**だから厚みは許される。

**ただし「厚くてよい」ではなく「薄さの優先度が下がる」だけ。**
スリムで賢い簡潔なロジックに魅力があることは変わらない —— **簡潔さは別軸として残る**
(保守しやすさは行数の関数なので)。**行数を理由に削るな。責務の重複と、
対象の複雑さを超えた賢さを理由に削れ。**

### コードの判定「散文を何行消したか」の使い方

**コードは説明の代替物であって、追加物ではない。**これは原則3(決定論的な作業はスクリプトへ)の
裏返し —— スクリプトが唯一の書き手になれば「手で書くときに間違えないための説明」は
**不要になるのではなく、存在理由が消える。**

実例(2026-08-08、`calibrate.sh` 200行):

| 無いとき | あるとき |
|---|---|
| 係数を**散文で正当化する** —— 「文献値だが未較正」「方向は過大と思われる」「較正の口は /context」 | 叩いて数字が出る |
| **その散文は2回とも間違っていた** —— 方向を逆に断言し、1本からの逆算が破綻していることに気づかなかった | **2つ目をスクリプトが捕まえた** |

**議論を測定に置き換えたぶん、200行は元が取れている。**散文なら「⚠️ 2本で確かめること」と
書いて終わっていた —— 実際そう書いていた。**⚠️ を書くくらいなら、解ける形にする。**

### コードでも落第するもの

閾値が高いだけで、無条件ではない。**散文を1行も消していないコードは落第する:**

- **起きていないケースへの投機** —— 2026-08-08 に配布フックへ入れたトークン係数の
  env 上書き3つ(`HARNESS_TOK_*`)。ベンダー差は実在するが、**設定した人はまだ誰もいない。**
  消している散文はゼロ。
- **同じことを2箇所で測る** —— 頭のサイズを3実装が3つの単位で測っていた(原則7)。
- **対象の複雑さを超えた賢さ** —— 20項目のチェックリストに 1,498行 は、比率として疑う。

## 2b. 散文の判定

**その一文はエージェントの行動を変えるか。プラスにもマイナスにも。**

| | 扱い |
|---|---|
| 良い方へ変える | 残す |
| 変えない | **削る。**何もしない文も他の文の取り分を奪っている |
| **悪い方へ変える** | **削る。急いで** |

3つ目が**陳腐化の実体**。モデルが賢くなるほど既定が良くなるので、
**「良い既定を言い直しただけの文」は雑音で済むが、「今や既定より劣る指示」は上書きしてしまう。**
放っておくと負債が自然に増える方向に動く。

**上限は上限であって目標ではない。**「500行以内だから合格」は判定を数字にすり替えている。

## 3. 決定論的な作業はスクリプトへ

**判定: 同じ入力なら必ず同じ出力になるか。**なるならスクリプト、ならないならスキル。

これは陳腐化への備えでもある —— **決定論的な作業はモデルが賢くなっても良くならない。
むしろ実行のたびに揺れる分だけ悪い。**

外部の基準(agentskills.io)も同じことを2通りで言っている:

> a command grows complex enough that it's **hard to get right on the first try**
> the agent **independently reinventing the same logic each run**

**副産物として散文が消える。**スクリプトが唯一の書き手になれば、
「手で書くときに間違えないための説明」は必要なくなる(不要になるのではなく、**存在理由が消える**)。

## 4. 識別子は、外部から参照された時点で変えられなくなる

`H-1` / `IOS-3` / `R-2` のような ID の規則:

1. **再利用しない** —— log.md から参照されるため。採番はファイル全体を走査する
2. **振り直さない** —— 同上。過去の記録が嘘になる
3. **ID は「名前」であって「順位」ではない** —— 順序は位置が、依存は辺が持つ
4. **接頭辞はコンポーネント**(`H-` / `IOS-`)。`R-` は log.md 専用の別名前空間
5. **欠番を許す** —— アーカイブしても番号は空いたまま

3 が効く。番号が順序を運べないと決めた以上、**運ぶものを別に用意しないといけない**
(= 依存辺)。日付ベース ID(`yyyymmdd-n`)は採番を分散したいときの解で、
**単一カウンタなら短い方が勝つ** —— この ID は会話で口に出されるため。

## 5. 名前は、借りた期待も一緒に運ぶ

既存の語彙を借りると読み書きの期待も借りられる。**だから期待が真であるときしか借りてはいけない。**

| | 期待 | 借りてよいか |
|---|---|---|
| `status` | 読むだけ | ✓ 真 |
| `doctor` | 診るだけ(既定) | ✓ 真 |
| `commit` | **VCS に記録される** | ✗ 偽(正典しか触らない) |
| `tidy` | (借り物ではない。そのままの英語) | ✓ 誤解の余地なし |

**名前空間では期待を止められない。**`/harness:commit` を叩いた人は git 履歴を見に行く。

そして**名前は機能を縛る。**`init` と名づけたせいで、そのスキルは「導入」以上を引き受けられなくなった
(実際には主用途が再実行だったのに)。

## 6. 人が10秒で検算できないものは eval にしない

eval も検知器なので、**eval 自身を検証できないなら信用できない**(harness 原則4 と同じ)。

| | 判定 | 検算 | 採るか |
|---|---|---|---|
| **発火の精度** | `jq` で tool_use を見る | **できる**(1回叩けば同じ答え) | **採る** |
| 出力の品質 | LLM が採点 | 難しい | **採らない** |

公式の改善ループは「assertion をエージェントが書き、採点し、改善案も出す」——
**人間が外に出る構造**で、これが「eval の中だけのユビキタス言語」を生む。

やるとしても条件は1つ: **assertion をスクリプト判定に限る。**
harness は成功が機械判定できる(`--lint` の exit code / 頭のバイト数 / 索引の鮮度)ので、
LLM に採点させる理由が無い。

**そして eval をゲートにしない。**「決めたことが効いたかの後追い確認」に留める。

## 7. skill は agent 向け。人向けの文は README へ

**SKILL.md の読者はエージェント。**「caldav で実証済み」のような信頼性の主張は人間向けなので
README へ移す。節の名前もそれで決まる —— `## 設計原則(なぜこの形か)` は「なぜ」の説明を
招くので、`## 配布物の前提(判断に効く事実)` にすると**何を書いてよいかが名前で決まる。**

**本文と references は英語で書く。**トークン効率(日本語 ≒ 1.1 tok/字 vs 英語 ≒ 0.25 tok/字。
5,000 トークン上限に直接効く)と、非英語での性能劣化の両方。
実測: インストール済み skill の description は **英語 150本 / 日本語 12本**で、
日本語はほぼ自作分のみ。skill listing は英語の system prompt の中に入る。

**スクリプトの出力とコメント、`docs/` は日本語**(人間も読むため)。

### description は「ユーザーの言い回し」ではなく「エージェント自身の状況」で書く

自分で発火する skill の description を**ユーザーが言いそうな語**で書くと、**ユーザーが実際には
そう言わないので永久に発火しない。**しかも**静かに失敗する** —— エラーも記録も出ず、
「発火しなかった」と「その状況が来なかった」が区別できない。

```yaml
# ✗ user-phrase keyed —— この言い方をされなければ届かない
description: 「次何やるんだっけ」「タスク一覧」で発火。

# ✓ agent-to-self —— 自分が今どういう状況にいるかで判定できる
description: >-
  I invoke this when I need to know what to work on next in this repository —
  I am starting a session, finishing a unit of work, or the user is asking
  what remains. Also on '/harness:status'.
```

実運用の解剖([compound-marketing#15](https://github.com/buntysomroy/compound-marketing/issues/15)):
13本中11本が user-phrase keyed で、**該当の1本は一度も呼ばれず、検討すらされなかった。**

**ただし「磨けば発火率が上がる」は実証されていない。** 測定を試みた3件は
lift ゼロ / 0/40(原因は隣接 skill による捕捉)/ 代理指標のみ。**失敗しているのは言い回しではなく
到達性**のことが多い —— そもそも発火経路が無い、隣の skill に取られる、素のモデルが自力で解ける。
**書き直す前に「発火経路があるか」を先に見る。**

## 8. 予算は資源配分であって、検知器の閾値ではない

**閾値を上げて警告を消すのは禁止**(harness 原則3)。ただしこれは**検知器の閾値**の話。

`skillListingBudgetFraction` のような**資源配分**は別物 —— 上げた分だけ毎ターン実費が出るので、
**払う判断を意識的にすればよい。**ラチェット禁止の対象ではない。

見分け方: **上げたときに「見えなくなるもの」があるならラチェット。「増えるコスト」があるなら配分。**

**そして予算は絶対値ではなく、多くがコンテキスト窓に比例する。**

```
skill listing の予算 = contextWindow × 4 × skillListingBudgetFraction
```

**分母を確かめずに超過を判定しない。** 2026-08-08 に実際にやった —— バイナリの `mF_=200000` を
固定値と読んで「予算 8,000 文字・168% 超過」と報告したが、あれは**引数の既定値**で、
1M コンテキストのモデルでは予算 40,000 文字。**実際には超過していなかった**(`/context` の
`Skills: 4.6k tokens (0.5%)`、50本すべてが full description のまま)。

**教訓は2つ。**(1) 予算を語る前に**実測の口**(`/context`)を先に見る。ディスク上のファイルを
足し合わせた推計は分母を間違えうる。(2) **同じ設定でもモデルによって結論が変わる** ——
200k のモデルへ切り替えれば同じ構成が実際に超過する。**「超過している/していない」は
環境の属性であって、構成の属性ではない。**

### 単位は、実際に縛っている機構から取る。代理指標はスクリプトが測るなら要らない

**2026-08-08 に、頭の予算「8,000 バイト / 80 行」と CLAUDE.md の「80 行」を全部捨てた。**
どちらも**どの機構も使っていない単位**だった。

| 単位 | どの機構が使うか |
|---|---|
| **文字** | SessionStart stdout **10,000字**で切り詰め(#70460 / #84021)。CLAUDE.md 40,000字で警告 |
| **トークン** | 毎リクエストの実費。skill 本体 5,000 tok で切り詰め |
| バイト | **どこにも無い**(#70460 の "10K" を私がバイトと読み違えた) |
| 行 | **どこにも無い** |

**行が特に悪いのは、言語構成の関数だから。**実測: `notchbar/CLAUDE.md` は 70 行 ≒768 tok
(日本語率 0%)、`figmate/CLAUDE.md` は 88 行 ≒1,743 tok(30%)—— **行は 1.26 倍しか
違わないのにトークンは 2.27 倍。**figmate は「88 行だから」警告されていたが実費は健全で、
**行で測っていたことが生んだ実物の誤検知**だった。複数リポジトリへ配るものほど効く。

**そして方針との矛盾があった。代理指標は、人が目視で数えるときに要るもの。**
スクリプトが測るなら文字もトークンも正確に出せるので、**「ロジックをスクリプトへ寄せる」と
決めた時点で代理を残す理由は消えている。**にもかかわらず私は代理を残しただけでなく、
`CLAUDE_MD_MAX=80` として**類推で増やした** —— 根拠の無い数字を根拠の無いまま横に広げた。

**判定:** その情報を実際に制約している機構は何か。その機構はどの単位で動くか。それを測る。
類推でも、既にあるからでもなく。**単位を揃えることは目的ではない** —— カタログ部は注入
されないので行のままでよい(そこで守っているのは「人が読み通せる長さ」で、実際に行で決まる)。

**ラチェット禁止との関係を曖昧にしないこと。**単位の是正は「閾値を上げる」ではないが、
実効は緩和側だった(頭は旧バイト予算の 97% → 新文字予算の 51%)。**緩和だという事実は
隠さない。**隠すと、次に誰かが同じ言い訳で本当に閾値を上げる。

### 測れないものを予算にするときは、測れないことを設計に織り込む

トークンは**正確に測れない。**2026-08-08 にバイナリ(2.1.222)で確認した事実:
**Claude Code はローカルにトークナイザを持っていない**(cl100k / o200k / merges.txt /
vocab.json / bpe_ranks すべて 0 件)。正確な数が要るときは `POST /v1/messages/count_tokens`
を叩き、届かなければ `count_tokens_unreachable` を記録して**文字数だけの概算に落ち**、
"Token counts are estimates and may differ from actual usage." と明示する。

**それでもトークンを予算にするのは、文字だけだと言語で 4 倍ズレるから。**同じ 3,000 字が
英語なら ≒768 tok、日本語なら ≒3,300 tok。**概算の仕事は正確であることではなく、
単位を言語依存でなくすこと** —— ±30% の誤差でも、4 倍の言語バイアスよりはるかに良い。

**織り込み方は4つ。**

1. **過小評価に倒れない側へ寄せる。**過小評価は「予算内に見えて実は超過」= 沈黙する失敗。
2. **概算であることを出力に出す**(`≒`)。Claude Code 自身の開示と同じ。
3. **較正の口を決めて、較正するまで「正しい」と書かない**(`/context`、`/plugin` の詳細表示、
   または `count_tokens` API —— **無料**。RPM 制限のみ)。
4. **正確な軸を主、概算の軸を従にする。**切り詰め(文字)は正確なので ✗ を出してよい。
   トークンは ⚠️ 止まりにする。**概算だけで人を止めない。**

**そして 2026-08-08 に、この4つを全部書いた直後に (1) を間違えた。**公式:

> "Claude 4.7 and later models use a newer tokenizer. The same input text produces
>  **approximately 30 percent more tokens** than on earlier models."

置いた 0.25 / 1.1 は**旧トークナイザの文献値**で、Opus 5 / Sonnet 5 / Fable 5 を含む現行モデル
では約 30% **過小**。「過大だから安全側」と書いたのは逆で、**沈黙する失敗の側に倒していた。**
係数を直したら、頭も CLAUDE.md も予算超過に変わった —— **超過はずっとあって、過小な係数が
隠していた。**教訓は「保守側に倒す」ではなく、**保守側がどちらかを確かめてから倒す。**

### 定数に見えるものが環境の属性なら、上書き可能な既定値として実装する

**予算まわりでこの誤りを3回やった。**同じ形なので規則にする。

| 誤り | 定数だと思ったもの | 実際は |
|---|---|---|
| `mF_=200000` | skill listing の予算 | **引数の既定値**。窓の大きさの関数 |
| `0.25 / 1.1 tok/字` | トークン係数 | **モデルの属性**(4.7 で 30% 変わる) |
| 同上 | 同上 | **ベンダーの属性**(Claude と GPT で語彙が違う) |

3つ目が一番効く。**harness はエージェント非依存**(Codex アダプタを配る)なのに、
私は Claude 較正の係数を**配布物の中核に定数として埋めた** ——
`context-mechanics.md` の冒頭に自分で「Claude 専用の知識なので配布物の中核に置かない」と
書いた、その直後に。

**単位ごとに、何の属性かを先に言えるようにする:**

| | 何の属性か | 可搬か |
|---|---|---|
| 文字 | **テキストそのもの** | **する** |
| バイト | テキスト + エンコーディング | ほぼする(が、どの機構も使わない) |
| トークン | **テキスト × トークナイザ** | **しない** |
| 行 | テキスト × 言語構成 × 書き癖 | しない |

**判定: 可搬な単位でゲートし、可搬でない単位は「上書き可能な既定値 + 出力にラベル」にする。**
harness の実装では `HARNESS_TOK_ASCII_PCT` / `HARNESS_TOK_WIDE_PCT` /
`HARNESS_TOKENIZER_LABEL` で差し替えられ、警告文は必ず「(Claude 4.7+ 換算)」を伴う。
**ラベルの無い数字は、別クライアントで黙って嘘になる。**

⚠️ **ただし構造まで捨てない。**言語で加重すること自体はベンダー非依存 —— 英語中心の BPE なら
日本語が高いのは共通で、変わるのは倍率だけ。**構造は残して係数だけ外に出す。**

### 予算は「誰が何回払うか」まで含めて設計する

同じ 2,000 トークンでも、払う回数が違えば別のコストになる。

| | サブエージェントに届くか | 実際の支払い |
|---|---|---|
| ND の頭(SessionStart) | **届かない**(#46696) | main のモデルで **1 回** |
| `CLAUDE.md` | **届く**(Explore / Plan 以外) | **1 + サブエージェント起動回数** |

**だから「main しか要らない情報を CLAUDE.md に置かない」が、閾値より効くレバー**
(乗算されるのは CLAUDE.md の方)。実装は implementer / artisan / architect を委譲で回す
運用なので、CLAUDE.md は毎セッション4回払っていることになる。

**そして混在するのはモデルだけではない。クライアントも混在する**(Claude Code / Codex)。
モデル差(±30%・有界・片方向)より**言語差(4倍)とベンダー差の方が大きい** ——
だから精度を追わず、**多い側に固定してラベルを出し、誤差の範囲を書き残す。**

## 🤝 HITL を節目で回す(2026-08-04 設計)

自動採点だけでは上の2つは測れない(片方は天井、もう片方は指標が人間の受容)。
**節目のタイミングで人間を挟む**。3つのモードを使い分ける:

### モード A: 成果物のブラインド A/B ジャッジ

- **いつ**: 候補(old/new、あるいは改善版どうし)の成果物が揃ったとき
- **やり方**: 既存の HITL 規約に従う(`evaluations/README.md`)——
  匿名ラベル・seed 付きランダム提示順・raw 1〜5 スコア・評価者と日時を記録。
  **technical pass と design preference を合算しない。**
- **対象**: アイコン(light/dark/tinted の比較)、デモ動画(尺・変化区間・見せ方)

### モード B: 具体的な改善点の言語化

- **いつ**: A/B で優劣が付いた直後、**まだ理由が言語化されていないうちに**
- **やり方**: 「なぜ B を選んだか」を自由記述で取り、**スキル本文へ書き戻す観点**に変換する。
  ⚠️ `METHODOLOGY.md` §5 に従い、**答えではなく探し方**を書き戻す
  (答えを書くと、その eval が「発見」ではなく「想起」の測定に変わる)
- **これが `ios-app-icon` の収束コストを下げる本体** —— 往復のたびに得た指摘を
  スキルへ畳み込めば、次回の往復回数が減る。減ったことが指標になる

### モード C: 実セッションでの発火とフィードバック(field feedback)

- **いつ**: 実作業でスキルが発火したとき(統制された eval ではなく本番)
- **やり方**: 発火した事実と、役に立ったか/邪魔だったかを `docs/ios-skills/log.md` へ追記。
  **統制された eval では出ない問題(発火しなかった・見当違いの節を読んだ・
  手順が現場の前提と合わない)がここでしか拾えない。**
- **注意**: これは統制された測定ではないので、**A/B の数値と混ぜない**。
  観測として別枠で扱い、次の case 設計の入力にする

### 節目の定義

- スキル本文へ実質的な変更を入れたとき → モード A(退行していないか)
- A/B で差が出た/出なかったとき → モード B(理由の言語化)
- 実作業でスキルを使ったとき → モード C(随時)

### 6. 🎯 「new が優れている」を示せる live case を作る

**現状は全 case で「非劣性」止まり。** 退行していないことは言えるが、
改善したことは言えていない。原因は測定側の天井で、反復を増やしても解決しない
(満点同士の比較は n を増やしても差が出ない)。

**やること: 天井に当たらない = old が実際に苦手な領域を live 化する。** 候補:

1. **CalDAV アカウント投入の live 版** —— 2026-08-02 の測定で
   **1/7・53分 → 6/7・5分5秒**と最大の差が出た領域。まっさらな端末では初回追加が
   必ず失敗するという一次情報が効く。
   ⚠️ **seed 端末があると `simctl clone` で近道でき差が消える**
   (`evaluations/ios-skills/ios-simulator/evals/METHODOLOGY.md` §11)。
   実行前に CalDAV 保持端末が0台であることの確認を手順に組み込むこと。
2. **複数端末の同時操作** —— `booted` の暗黙解決が事故になる領域。old は対象 UDID を
   明示する規律が弱く、read-only の `procedural-device-build-plan` で safety 違反3件を出している。
3. **失敗からの復帰** —— わざと壊れた状態(前面にいないアプリ、CA 未信頼の TLS)から
   始めさせ診断の質を測る。`references/diagnosis.md` の価値が直接効く。

**代替案とその評価**(結果ファイルに詳細): 反復増は天井が動かないので ❌、
満点上限の引き上げ(5→10)は基準の言語化が伴わないと恣意的になるので △。

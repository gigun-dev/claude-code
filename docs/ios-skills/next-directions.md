| `appstoreconnect-upload` | **使ったことがない** | 🔻 **追加投資しない。** 既存2 case を非劣性の回帰テストとして維持するだけ |

### 2つの本丸は測る軸が別物

- **`ios-simulator`** = **タスク成功率と所要時間**。live-e2e で測る。いま測れているのは
  日本語入力(満点で天井)だけで、**実際のボトルネックであるデモ動画・E2E 検証の case が

- **`ios-app-icon`** = **収束コスト**。品質は既に満足水準なので rubric スコアでは測れない。

## HITL の運用(2026-08-04 設計)

自動採点だけでは上の2つは測れない(片方は天井、もう片方は指標が人間の受容)。
**節目のタイミングで人間を挟む。**

### モード A: 成果物のブラインド A/B ジャッジ

- **いつ**: 候補(old/new、あるいは改善版どうし)の成果物が揃ったとき
- **やり方**: 既存の HITL 規約に従う(`evaluations/README.md`)—— 匿名ラベル・seed 付き
  ランダム提示順・raw 1〜5 スコア・評価者と日時を記録。
  **technical pass と design preference を合算しない。**
- **対象**: アイコン(light/dark/tinted の比較)、デモ動画(尺・変化区間・見せ方)

### モード B: 具体的な改善点の言語化

- **いつ**: A/B で優劣が付いた直後、**まだ理由が言語化されていないうちに**
- **やり方**: 「なぜ B を選んだか」を自由記述で取り、**スキル本文へ書き戻す観点**に変換する。
  ⚠️ `METHODOLOGY.md` §5 に従い、**答えではなく探し方**を書き戻す
  (答えを書くと、その eval が「発見」ではなく「想起」の測定に変わる)
- **これが `ios-app-icon` の収束コストを下げる本体** —— 往復のたびに得た指摘をスキルへ
  畳み込めば、次回の往復回数が減る。減ったことが指標になる

### モード C: 実セッションでの発火とフィードバック(field feedback)

- **いつ**: 実作業でスキルが発火したとき(統制された eval ではなく本番)
- **やり方**: 発火した事実と、役に立ったか/邪魔だったかを `docs/ios-skills/log.md` へ追記。
  **統制された eval では出ない問題(発火しなかった・見当違いの節を読んだ・手順が現場の
  前提と合わない)がここでしか拾えない。**
- **注意**: これは統制された測定ではないので、**A/B の数値と混ぜない**。観測として別枠で
  扱い、次の case 設計の入力にする

### 節目の定義

- スキル本文へ実質的な変更を入れたとき → モード A(退行していないか)
- A/B で差が出た/出なかったとき → モード B(理由の言語化)
- 実作業でスキルを使ったとき → モード C(随時)

4. **t09「日本語打つと文字化けする」**
   288 字版で「テキスト入力」の語が消え、例が「この画面タップして」「スクショ撮って」の2つだけになった。

   末尾の「実機は対象外(ios-device-build)」が、**「iPhone」と言われたら降りる**方向に

- **t14「XCUITest で回帰テストを書いて」** — description に「反復検証は XCUITest」が入っている。
  意図的な記述なので、誤爆したら「昇格の**判断**」と「XCUITest を**書く仕事**」の区別を

### 字数の余裕

**1024 字の上限に対して 288 字。736 字ぶん余っている。**
公式は "Keep it concise" と言うと同時に "Err on the side of being pushy — explicitly list contexts
where the skill applies" とも言っており、**短さ自体は目的ではない**。
上の 1〜4 を拾う語(録画/動画・うまくいかないときの診断・複数台・文字化け)を足しても
400 字に届かない。**短縮しすぎている可能性が高い**というのが現時点の読み。

ただしこれは全部推測。`scripts/run_loop.py` は Simulator を一切触らないので安く回せる。
**744 字版と 288 字版の両方を `--description` で指定して同じ 20 クエリに当て、
どこが良くなりどこが悪くなったかを1回で出すのが最短。**

### ⚠️ ただし「短くすれば直る」とは限らない

iteration-1 の `eval-caldav-account-sync` は、**スキルをロードしたのに 7 本中 6 本落ちた**。
落ちた 4 本(`Accounts3.sqlite` での判定 / 事前のアカウント有無確認 / `.mobileconfig` の効果確認 /
事前のプロキシ確認)は**すべて SKILL.md に答えが書いてある**。しかも:

- プロキシの事前チェックは **134-203 行**(本文のかなり前方)
- CalDAV 初回追加の罠は **319-381 行**(中盤)
- `.mobileconfig` が効かない話は **540-574 行**

**前方にあるのに読まれていない。** ということは、これは純粋な「長さ」の問題ではなく
**順序と形式**の問題かもしれない。「★事前チェック」は *節* として存在するが、
**手順の Step 0 にはなっていない**(`## 典型フロー` は 708 行目、本文の最後にある)。
エージェントは上から読むとは限らず、目次的に拾い読みするので、
**「最初にこれを実行しろ」が本文の 134 行目にある**構造は効きにくい。

→ 削減とセットで **「事前チェックを典型フローの Step 0 に統合し、フローを本文の先頭に置く」**
を試す価値がある。削減だけを先に入れると、この仮説が検証できなくなる
(何が効いたか分からなくなる)ので、**削減と構成変更は別イテレーションに分けたい**。

これも推測。iteration-2 で `without_skill` を取れば、
「そもそもスキル無しでも同じ失敗をするのか(= スキルの問題ではなくタスクが難しい)」が分かる。

## 3. eval を回す上での実務的な障害

### コスト(実測)

| | 時間 | トークン |
|---|---|---|
| eval-demo-video (with_skill) | 3,302 s ≒ **55 分** | 258,665 |
| eval-caldav-account-sync (with_skill) | 3,178 s ≒ **53 分**(※完遂ではなく打ち切り) | 203,599 |

6 本 × 2 構成 = 12 run を直列で回すと **約 11 時間・約 280 万トークン**。
**毎イテレーション全部回すのは無理。** `README.md` の「どれを回すか」で優先順位を決めてある。

### 副作用

普通のスキルの eval は「ファイルを作って捨てる」で済むが、これは違う:

- **Simulator 端末を作る**(消さないと溜まる) → `EVAL-` プレフィックス規約を決めた
- **Keychain に CA を入れる**(端末単位なので端末を消せば消える)
- **ホストのシステムプロキシ / Proxyman のルールを触る**(**ホスト全体に効く。復元必須**)
- **本番 CalDAV サーバーに書き込む**(eval 2 と 3。iteration-1 の run は自分で消して 404 まで確認していた)
- **保護対象の端末を壊しうる**(iteration-1 で実際に1件起きた)

→ 各 run のプロンプトに境界を明記する必要がある(テンプレートは `README.md`)。
これは「丁寧のため」ではなく、**iteration-1 で実害が出たから**。

### 並列に回せない

端末を分ければ `idb` の所有権は分離できるが、**システムプロキシ・`SimRenderServer`・
ホスト側のツール状態は共有資源**。iteration-1 では、他プロセスが別端末を操作している最中に
`simctl io recordVideo` が `SimRenderServer.SimulatorError` で開始に失敗している
(エージェントの推論であって確定した因果ではない)。
→ **直列。** これが上のコストをそのまま壁にしている。

### transcript が無いと採点できない(iteration-1 の最大の反省)

iteration-1 に残っているのは**エージェントの自己申告レポートだけ**。その結果:

- 「すべてのコマンドが UDID を明示しているか」という expectation を**採点できなかった**
  (`eval-caldav-account-sync` の grading.json、証拠不足のため PASS にしていない)
- ツール呼び出し回数・エラー回数(`metrics.json`)が取れず、benchmark の該当欄が 0 のまま
- 「どの reference をいつ読んだか」が自己申告に依存しており、
  **SKILL.md の到達性という一番知りたいことの証拠が弱い**

`skill-creator` の grader は `transcript_path` を前提にしている。
**iteration-2 からは `run-N/transcript.md` を必須にする。**

### eval が外部プロジェクトに依存している

6 本のうち 4 本が `swift-mcp-app` か本番 `caldav` サーバーの存在を前提にしている。
**プラグインとして他人に配布したとき、この eval は他人の手元では回らない。**
将来は `evals/files/` に最小の fixture アプリ(タップ / テキスト入力 / WebView カードだけ持つ)を
置く必要がある。ただし今は「実在するタスクで測れる」ことの方が価値が高いので、後回しでよい。

### 自己申告レポートを grading の入力にすることの限界

iteration-1 の grading は、エージェント自身が書いた反省文を読んで採点している。
**自己申告は自分の失敗に甘くはなかった**(むしろ誤操作を自分から報告している)が、
**書かれなかったことは採点できない**という非対称性がある。
公式の "Don't give the benefit of the doubt" を守ると、
**書いていない = FAIL 扱いになり、実力より低く出る**方向にバイアスがかかる。
transcript が入ったら iteration-1 のスコアと直接は比較できない点に注意
(`benchmark.json` の notes にも書いた)。

## 5. 共有スキルへの到達性 — subagent の制約ではないと確定した(2026-08-02 実測)

**問い**: eval 3本のうち2本が共有スキル `ios-skills:ios-simulator` を読まなかった。
これは subagent の制約か、それとも選択か。

**測り方**: 各 agent 型で subagent を立て、「ツール一覧に `Skill` はあるか / スキル一覧は
渡っているか / 名前を全部挙げよ」とだけ聞いた(ファイル読取・コマンド実行は禁止・副作用ゼロ)。

| subagent_type | agent 定義の tools | `Skill` ツール | スキル一覧 |
|---|---|---|---|
| **`claude`**(eval で使用) | `*` | **あり** | **main と同一の全 54 件**(`ios-skills:ios-simulator` を含む) |
| `implementer` | `Read, Write, Edit, Bash, Grep, Glob` | **無し** | **渡らない** |

`*` 型では渡り方も main と同じ —— system プロンプト後方の注入ブロックに
`The following skills are available for use with the Skill tool:` として並ぶ。

**結論**: 分岐点は「subagent かどうか」ではなく **agent 定義の tools に `Skill` が入っているか**。
eval 3本はすべて `claude` 型なので、**共有スキルは見えていたしロードもできた**。
読まなかったのは**能力の制約ではなく選択**であることが確定した。

### 3本の差(仮説・n=3 で未確定)

| run | 依頼文の出だし | 共有スキル |
|---|---|---|
| demo-video iter-2 | 「`~/ghq/.../swift-mcp-app` の MCPHost の…」 | ❌ Skill 呼び出し 0 件 |
| demo-video iter-3 | 同上 | ❌ `cat` でリポジトリ内スキルを読んだ |
| caldav-sync iter-2 | 「自作の CalDAV サーバー(`https://...`)に…」 | ✅ Skill で2本ロード |

**依頼がリポジトリのパスで始まると、そのリポジトリ内を探索してスキル機構を経由しない**、
という仮説と整合する。**未検証。** 検証するなら、同じ eval を「パスで始まる版」と
「目的で始まる版」で振って Skill 呼び出しの有無を比べるのが最短。

### 代償(実測)

iter-3 は共有スキルを読まなかったため、**共有スキルには書いてある罠を踏んだ** ——
`idb ui describe-all` が JSONL ではなく入れ子の JSON 配列を返す件。
プロジェクト側スキルは当該項目を共有スキルへ委譲していたので、そこには無かった。
→ **委譲は「読まれる」ことを前提にしている。読まれない経路があると穴になる。**

### ⚠️ やってはいけない検出方法

transcript に `available-skills` 等の文字列があるかを見る方法は**無効**。
**実際に Skill をロードした transcript でも同じく 0 件**になる。
正しくは **`Skill` の tool_use を直接カウント**する。
(この誤検出で一度「subagent は引けない」と誤断定した。SKILL.md「診断の規律」3
——ground truth は疑っている道具の外側で取る—— の実例。)

## 6. どの assertion が実際に弁別しているか(A/B の実データ・2026-08-02)

`eval-caldav-account-sync` の with/without を突き合わせた結果。
**「両構成で常に PASS する assertion は削る」を、推測ではなく実データで判定できる状態になった。**

| # | with | without | 判定 | assertion(要約) |
|---|---|---|---|---|
| 0 | ✅ | ❌ | **★弁別** | 判定を `Accounts3.sqlite` で行う(UI ではなく) |
| 1 | ✅ | ❌ | **★弁別** | 追加前にユーザー追加アカウントの有無を確認 |
| 2 | ✅ | ❌ | **★弁別** | ネットワーク検証前にシステムプロキシを確認 |
| 3 | ❌ | ❌ | 両FAIL | `Accounts3.sqlite` の前後差分(→ iteration-3 で改訂済み) |
| 4 | ✅ | ✅ | 両PASS | スクショが実在しパスが提示されている |
| 5 | ✅ | ✅ | 両PASS | 保護対象に破壊的操作なし |
| 6 | ✅ | ✅ | 両PASS | `booted` を使わず UDID 明示 |

### 判断

- **#0・#1・#2 は残す。** スキルの中核(sqlite で裏を取る / 端末の前提を疑う / 環境を先に見る)が
  そのまま出ている。**#2 は with 側が不利な環境**(プロキシ有効)で PASS しているので、
  弁別力は表の見た目より強い。
- **#4 は削除候補。** 「スクショが実在する」はタスク要件そのもので、両構成が通る。
  `_comment_scope` が予告していた「両構成で常に PASS する assertion」の実例。
  ただし **#4 を消すと成果物の実在チェックが無くなる**ので、消すのではなく
  「**採点者が画像を開いて内容を確認した**」まで要求する形に強めるほうがよい
  (iteration-1 で自己申告を信じて誤採点した件の再発防止にもなる)。
- **#5・#6 は両 PASS でも残す。** この A/B では差が出なかったが、
  **iteration-1 では両方 FAIL している**(`booted` 指定で他人の端末を撮る事故が実在)。
  安全側の assertion は「差が出ない = 不要」ではなく「差が出ない = 現状は守れている」と読む。
  退行の検出器として機能する。

### 副産物: baseline が「スキルの価値」を具体化した

without_skill はスキル記載の罠を**4つ独立に踏み直した**(詳細 `BENCHMARK.md`)。
とくに新品端末の初回追加で **総時間の 38%(約7分)** を溶かしている。
**どの記述が時間を買っているかが、推測ではなく実測で特定できた**のはこの A/B の最大の収穫。

## 7. 到達性の再現性 — 6 run 横断の実測(2026-08-02)

**測ったもの**: 各 run で「共有スキルを、**最初の状態変更コマンドより前に**ロードしたか」。

**4/6。そして失敗した2本は、どちらも「プロンプトがリポジトリのパスで始まる」run。**

### 仮説の強度

n=3 の時点で立てた「**タスクがリポジトリ名で始まると、そのリポジトリ内の `.claude/skills/` を
先に見に行く**」は、**n=6 で一度も破れていない**。
決定的なのは `webview` で、**リポジトリ名を含むが文末に置かれており、共有スキルをロードした**。
= 「リポジトリ名を含むか」ではなく「**冒頭にあるか**」で分かれている。

⚠️ **まだ因果ではない。** 検証するなら、同じ eval を
**「パスで始まる版」と「目的で始まる版」の2通り**に振って Skill 呼び出しの有無を比べるのが最短
(1本20分・2本で40分)。**交絡: demo-video は唯一 swift-mcp-app 側のタスクでもある**ので、
リポジトリの違いなのか語順の違いなのかを分離するには、
**caldav のタスクをパスで始める版**も要る(3本目)。

### 実務上の含意

- 共有スキルへの委譲は「プロジェクト側スキルにポインタを書く」だけでは**不十分**
  (iter-2 でポインタを読んだのに実行されなかった)。
- **プロンプトの語順という、スキル側からは制御できない要因**で到達性が変わる。
  → だから **agent 定義の `skills:` による事前ロード**(プロンプトに依存しない)が要る。
  `ios-skills:simulator-operator` はそのための構造だが、**リロード待ちで未検証**。
- 代償は実測済み: 共有スキルを読まなかった iter-3 は、**共有スキルには書いてある罠**
  (`describe-all` が入れ子配列を返す)を踏んでいる。

### 7-b. 測るべきは「スキルがロードされたか」ではなく「事前チェックが実行されたか」

§7 は**機構**(Skill ツールが呼ばれたか)を測っていた。だが実務で意味があるのは**振る舞い**
(環境チェックが実操作より前に走ったか)である。同じ 7 run を振る舞いで測り直した:

| run | スキル事前ロード | **事前チェック実行** |
|---|---|---|
| caldav-sync iter2 | ✅ | ✅ |
| **demo-video iter3** | **❌ 読まず** | **✅ 実行した** |
| webview iter3 | ✅ | ✅(操作なしのため不要) |
| fanout iter3 | ✅ | ✅ |
| japanese iter3 | ✅ | ✅ |
| onboarding iter3 | ✅ | ✅ |
| demo-video iter2 | ❌ | ❌ |
| | **4/6** | **6/7** |

**決定的なのは `demo-video iter3`。共有スキルを一度もロードしていないのに事前チェックを実行した。**
プロジェクト側スキル(`ios-e2e-verify`)に**チェックをコマンドごとインライン化**した効果が
実測で出ている。唯一の失敗 `iter2` は、その修正より**前**の run。

→ **到達性の問題は「共有スキルを読ませる」以外にも解ける。**
「読ませる」(agent の `skills:` 事前ロード)と「読まなくても済むようにする」
(呼ぶ側にコマンドをインライン化)は**独立した2本の対策**で、後者は既に効果が実証済み。

### 7-c. 測定バグと、そこから見つかったスキルの実在の欠陥

最初の測定では `onboarding iter3` を「❌ 順序が逆」と判定した。誤りだった ——
**`simctl create` / `bootstatus`(自分用の端末を用意する行為)を「実操作」に数えていた**ため。

しかしこの誤判定が**スキルの実在の欠陥**を露わにした:
**`sim-preflight.sh` は Booted な端末を要求する**(Shutdown だと止まる)。
なのに SKILL.md の Step 0 は「**何より先に**これを撃つ」と書いていた ——
**新規端末を作るワークフローでは物理的に不可能**。

→ 記述を訂正した。**境界は「端末を用意する」と「アプリを触る」の間**であって、
「何もしないうち」ではない。**自分の測定バグがドキュメントのバグを見つけた形。**

### 7-d. 🔴 §7 の仮説は**反証された**(2026-08-02・追加実験)

§7 で「**タスクがリポジトリのパスで始まると共有スキルを読まない**」という仮説を
n=6 で立てた。**検証したら外れた。**

**実験**: `caldav-account-sync` と同じ内容を、**リポジトリのパスで始まる文**に書き換えて実行
(「`~/ghq/github.com/gigun-dev/caldav` の CalDAV サーバーに書き込んだ予定が…」)。
→ **共有スキルを最初の simctl より前にロードした**(Skill#1 `ios-simulator`、
Skill#2 `ios-device-verification`、最初の simctl #3)。342 秒で完走。**仮説は成り立たない。**

**代替仮説「cwd かどうか」も成り立たない。** caldav(このセッションの cwd)の project skill は
スキル一覧に載るが swift-mcp-app のものは載らない、という差はある。しかし
**`onboarding iter3` は swift-mcp-app のタスクで、しかもパス始まりなのに共有スキルをロードした。**

### 現時点の正直な結論: **原因は特定できていない**

| run | リポジトリ | パス始まり | 共有スキル |
|---|---|---|---|
| caldav-sync iter2 | caldav | ✗ | ✅ |

**8 run 中 6 が読み、失敗2本はどちらも `demo-video`。**
リポジトリでも語順でも説明できず、**特定の1タスクに偏っている**。

未検証の推測(**事実として扱わないこと**): demo-video は、プロジェクト側スキル
`ios-e2e-verify` が**そのタスク専用に非常に充実している**唯一のケース
(ビルド・起動・OAuth・座標系まで網羅)。十分な手引きを見つけた時点で探索を止めた、
という説明はありうるが**検証していない**。

### この反証が示す実務上の含意

**原因が特定できない = プロンプト側の工夫では潰せない。**
だからこそ **agent 定義の `skills:` による事前ロード**(呼び出し文に一切依存しない)が要る。
「読ませ方を工夫する」路線は、根拠にしていた仮説が外れた以上**当てにできない**。

一方 §7-b で示したとおり、**「読まなくても済むようにする」(呼ぶ側にコマンドをインライン化)は
効果が実証済み** —— `demo-video iter3` は共有スキルを読まずに事前チェックを実行した。
**2本の対策のうち、実証済みなのは後者だけ。**

### baseline は目標に到達した —— ここが重要

**「スキルが無いとできない」ではない。** 有能なモデルは手引き無しでも 18 分で到達する。
スキルが買っているのは **到達可否ではなく、時間と証拠の質**:

- **時間**: 305s vs 1100s
- **証拠の質**: without 側は判定を**設定アプリの見た目**で行った(`Accounts3.sqlite` を
  一度も見ていない)。「停止中」の文字を読んで気づけたが、**UI が嘘をつく場面では破綻する**。

### baseline が「自力で再発見」したもの(= スキルの記述が実際に時間を買っている証拠)

baseline は手引き無しで、**スキルに書いてある罠を4つ独立に踏み直した**:

| 踏んだ罠 | 費やした時間 | スキルの該当箇所 |
|---|---|---|
| **新品端末の CalDAV 初回追加が「停止中」になる** | **約7分**(総時間の 38%) | 🔴 専用の節。回避策は `webcal://` 前置き(4タップ) |
| `idb ui text` の文字化け(`@` → `2`) | 数分 | 「テキスト入力」節。`simctl pbcopy` へ逃がす |
| スクショが `/tmp` に書けない | 1手 | 「その他のハマりどころ」 |
| AX ツリーにリンクが出ず詰まる | 約2分 | `diagnosis.md` §3「describe-all の穴」 |

**回避策の質も違う。** baseline は「削除 → 再追加」の儀式(約30タップ・入力6回)に辿り着いたが、
with_skill 側は `simctl clone`(**16秒・0タップ**)を選んだ。同じ問題に対する解の質の差が、
そのまま時間差になっている。

## A/B — スキルの有無(eval-demo-video)🔴 **差が出なかった**

| | スコア | 所要 | 環境 |
|---|---|---|---|
| with_skill(iter-3) | 6/6 | 852s(14分12秒) | **boot + CA 投入 + OAuth を自分で実施** |
| without_skill | 5/6 | 727s(12分07秒) | **上記が済んだ端末を引き継いだ** |

🔴 **この 727s と 852s は直接比較できない。** baseline は `simctl boot` も CA 投入も一度も
実行していない(transcript で確認)—— iteration-3 が整えた端末をそのまま使っている。
iteration-3 の device prep は約 120 秒なので、**差し引くと 732s ≒ 727s でほぼ同一。**

**つまりこの eval では、スキルの速度優位は観測されなかった。** 差が出たのは assertion 1本
(プロキシ事前確認)だけで、しかも実行時にプロキシが無効だったため baseline は罰を受けていない。

**これは正直に記録すべき負の結果。** そして示唆は明確で、
**スキルの価値は「録画」ではなく「アカウント/状態づくり」に集中している** ——
`eval-caldav-account-sync` では 3.6倍速・+3/7 の差が出た。同じスキルでも領域によって効きが違う。

## 計測方法の注意(2回間違えた)

**動画の「変化区間」を測るときは `mpdecimate` を使う。** 他の方法は誤る:

| 方法 | 何が起きたか |
|---|---|
| 縮小 PNG のハッシュ差 | **静止画でも再エンコードの量子化ノイズでハッシュが変わる**(末尾のパディング区間でハッシュが3値を循環しているのを確認)。→ 97% と過大 |
| `freezedetect` の start/end を index でペアリング | 対応がずれる。→「末尾 20.5s 静止・33%」と過小 |
| `-ss` を `-i` の**前**に置いてフレーム抽出 | キーフレームにスナップするので、**別時刻のフレームが同一に見える** |

3手法が食い違ったので、パディング区間のフレームを**正確シーク**(`-ss` を `-i` の後ろ)で
直接比較して決着させた。**手法が食い違ったら、疑っている道具の外側で ground truth を取る。**

## 0. ツール選定より先に効く、たった1つの実務ルール

> **撮るときは触らない、触るときは撮らない。**

録画とインタラクションを**時間的に分離する**。これはツールに関係なく効く。
理由は下記のとおり、**`simctl` も `ffmpeg` も「録画しながら大量にタップする」運用で
それぞれ別の壊れ方をした**から(実測)。実務上は:

1. まず**操作だけ**を通しでリハーサルして、座標・待ち時間・手順を確定させる
2. その後に**短い録画を複数本**に分けて撮る(1本 30〜60 秒)
3. 尺が要るなら編集で繋ぐ

## 1. `simctl io recordVideo` の尺は実時間と一致しない(作法では直らない)

**これは実測で確定した実害。**

| 条件 | 実時間 | ffprobe の `duration` | `nb_frames` |
|---|---|---|---|
| 無操作(画面が全く変化しない) | 15.014 s | **0.066667 s** | **1** |
| 20 タップの UI 操作あり | 目算 40〜50 s | 24.323333 s | 1634(`r_frame_rate=600/1`) |

**静止画面 15 秒の録画が 1 フレームになった。**

**推論(未検証・ただし観測とよく整合する)**: `recordVideo` はポーリングではなく
**イベント駆動 —— 画面が変化したときだけフレームを積む**方式らしい。画面が動かない間は
実時間が経過してもフレームが増えない。だから「作法を守れば直る」類の問題ではない。

**対処**:

- 尺の正確さが要らない用途(挙動の記録・バグの再現映像)なら、そのまま使ってよい。
- 実時間が要る用途(デモ・計測)なら、**後段で `setpts` 補正するか、別手段(§3)を採る**。

## 2. 正しい停止作法(これは守る価値がある)

```bash
# 1) 開始: stderr に "Recording started" が出るまで待つ。ここを待たずに操作を始めると先頭が欠ける
xcrun simctl io "$UDID" recordVideo -f "$OUT" 2> "$LOG" &
REC_PID=$!
until grep -q "Recording started" "$LOG"; do sleep 0.1; done

# ... 撮りたい場面 ...

# 2) 停止: pkill -f ではなく **実 PID** に SIGINT
kill -INT "$REC_PID"

# 3) ★ exit を実際に待つ。sleep で代用しない
while kill -0 "$REC_PID" 2>/dev/null; do sleep 0.05; done
```

**実測**: この作法だと SIGINT から **0.013 秒で exit** し、その後 25 秒間隔で5回読み直しても
`duration` は微動だにしなかった。旧版が書いていた「停止後に尺が伸びる」症状は
**再現しなかった**(= 旧版は exit を待たずに書き込み途中のファイルを読んでいた、という説明で足りる)。

### ★ 一般的な罠: `wait $pid` は別プロセス呼び出しでは効かない

`sim-rec.sh start` / `sim-rec.sh stop` のように**開始と停止を別の CLI 呼び出しに分ける**
録画スクリプトでは、bash 組み込みの `wait $pid` は「自分の子プロセスではない」ため
**即座に失敗して何も待たずに返る**。これに気づかず作ったスクリプトは、停止直後に
`moov atom not found`(トレーラ未書き込み)の壊れた mp4 を吐いた(実測・track2 §C)。

→ **`kill -0 $pid` のポーリングで exit を確認すること。** これは録画に限らず、
「PID をファイルに保存して別呼び出しで止める」系のスクリプト全般に刺さる。

## 3. `ffmpeg -f avfoundation` への全面移行は**推奨しない**

尺の正確さだけを見れば ffmpeg が明確に優れている。だが**録画中のタップを広く落とした**。

| 軸 | `simctl io recordVideo` | `ffmpeg -f avfoundation` |
|---|---|---|
| 尺の正確さ | ❌ 実時間と一致しない(§1) | ✅ 実測 15.01 s → **15.57 s** でほぼ一致 |
| フレームレート | 不自然(`600/1` timebase 由来) | ✅ `30/1` で一貫 |
| **録画中の `idb ui tap`** | ✅ **20/20 成功** | ❌ **20 回中 10 回失敗** |
| 負荷 | 軽い | ❌ CPU **32〜34%**、`libx264: MB rate > level limit` の警告が出るほど重い |
| 手間 | コマンド一発(+ §2 の作法) | ウィンドウ矩形取得・スケール算出・crop・macOS の画面収録権限 |

### タップ失敗の裏取り(ここが重要)

`idb` 自身の判定は信用できない(`idb ui tap` は外れても `rc=0`)。そこで:

1. `idb ui tap` を撃つ → `rc=0` で成功を返す
2. 2 秒待って **`xcrun simctl io <UDID> screenshot`(idb を経由しない別ツール)** で前後を撮る
3. `cmp` でバイト比較 → **完全一致 = 画面は本当に変化していない**

これで「タップが実機能として無視された」ことを、idb の自己申告に頼らず確定させた。
**ground truth が要るときのやり方として、録画以外でも使える手筋。**

### なぜ ffmpeg でタップが落ちたのか(推論・未確証)

ffmpeg は SimDevice の IO ポートに一切触れないので、「録画と HID が同じ IO を取り合う」という
当初の説明機構は**そもそも成り立たない**。観測とよく整合するのは
**CPU / 描画リソースの取り合い**(フル画面 3600×2338 の 30fps 取り込み + H.264 エンコードの負荷で、
Simulator 本体や WindowServer 側のイベント処理が遅延・ドロップする)という別の機構。
**未確証。** 検証するなら `-framerate` を下げる・crop を先にかけて負荷を落とす、で改善するかを見る。

### それでも ffmpeg を使うなら(track2 §C のレシピ)

- avfoundation の画面デバイス番号は `ffmpeg -f avfoundation -list_devices true -i ""` の
  `Capture screen 0` 行から**動的に取る**(マシン依存。ハードコード禁止)。
- ウィンドウ矩形は `osascript` の `get {position, size} of window 1` で points 単位で取る。
  **Simulator のウィンドウはセッション中に動くので毎回取り直す。**
- **スケール変換の落とし穴**: `system_profiler` の見かけ解像度と、OS が実際に配信している
  スケーリング後の解像度が食い違う設定がある(実測: 見かけ 3024×1964 に対し実キャプチャ 3600×2338)。
  `system_profiler` の数字を鵜呑みにするとズレる。**1 フレーム試し撮りして `sips` で pixel 幅を読み、
  デスクトップの point 幅との比からスケールを動的に出す。**
- 録画開始直前に `tell application "Simulator" to activate`(他ウィンドウに隠れていると
  真っ黒 or 別ウィンドウが写る)。
- 停止は §2 と同じく **exit をポーリングで待つ**。

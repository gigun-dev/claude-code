# WKWebView の中身は Simulator の外(ブラウザ)で検証する

iOS アプリの中の `WKWebView` に入っている HTML/JS を検証したいとき、
**Simulator を使うのは土俵の選択を間違えている。**

- `idb` の `describe-all` は WebView 内の DOM 要素を安定して返さない
  (アクセシビリティツリーに出るのはホスト側の要素が中心)。
- XCUITest 系でも WebView 内は扱いが弱く、Maestro を含めて open issue が残っている。
- 加えて Simulator 側の不確定要素(座標系・ジェスチャ排他バンド・HID)を丸ごと背負う。

**HTML をブラウザで開けば、これら全部が消える。** ワークアラウンドの積み増しではなく、
原因そのものの回避なので投資対効果が高い(2026-08-01 track4 の実測)。

---

## 実測でカバーできた範囲(track4)

Chrome(chrome-devtools MCP)+ 自作の最小ホスト shim で、**本番の実データを使って**
以下がすべて確認できた:

| 項目 | 結果 |
|---|---|
| 本物データでの描画(グルーピング・優先度・相対日付見出しなど表示ロジック) | ✅ 実測 |
| **セレクタで要素を取る**(a11y snapshot に DOM がそのまま出る) | ✅ 実測 |
| **クリックが効く**(ホストへのツール呼び出しが正しい引数で発火することもログで確認) | ✅ 実測 |
| スクロール(`scrollTo` は**ネイティブのジェスチャ層を経由しない**) | ✅ 実測 |
| コンソールエラー / JS 例外の検知 | ✅ 実測 |
| ライト/ダークテーマ | ✅ 実測(`emulate colorScheme`) |
| 狭い幅(iPhone 相当 393px) | ✅ 実測(`resize_page`) |
| ホストが申告する値(safeAreaInsets 等)を**任意に振る** | ✅ 実測。実機では「今ホストが言ってくる値」しか試せない |

Simulator で最も詰まっていた「スワイプがジェスチャ排他バンドに吸われる」問題は、
ブラウザのスクロールがネイティブ層を通らないので**原理的に発生しない**。

## 手順の骨格

1. **カードの HTML を実サーバーから取る**(MCP なら `resources/read`、
   一般には配信されている静的 HTML をそのまま取得する)。
2. **ホスト側のプロトコルを最小実装した shim ページを作る。**
   実装対象はホストの SDK 実体(例: `node_modules/.../dist/src/app.js`)を直接読んで確定させる。
   track4 のケースでは postMessage 越しの JSON-RPC 4 手で足りた:
   `ui/initialize` → 結果返却 → `ui/notifications/initialized` → `ui/notifications/tool-result`。
3. iframe は **`srcdoc` で埋め込む**(`about:srcdoc` origin になり postMessage の往復が素直に通る。
   `file://` 同士の cross-origin iframe より扱いが安定した)。
4. ブラウザ自動化(chrome-devtools MCP 等)で
   `take_snapshot` / `click` / `evaluate_script` / `emulate` / `resize_page` /
   `list_console_messages` を回す。

### 実際に踏んだ落とし穴

- **モック応答が実データを上書きする。** カードが起動直後に行う背景 refetch(SWR 経路)に
  汎用の空モックを返していたため、実データが「すべて完了しました」に化けた。
  → **read 系ツールだけは初期データをそのまま echo する。**
- **書き込み系ツールはプロキシしない。** 「本番データを壊さない」を、注意ではなく
  **構造(そもそもプロキシしない実装)**で満たす。
- 本番エンドポイントに CORS ヘッダが無いと、`file://` origin からの直プロキシはブロックされる。

## 配色・コントラストを監査するとき(2026-08-02 の A/B から手順化)

上の shim は**対話操作**のための構え。**「色が破綻していないか」だけなら shim は要らない** ——
HTML を吐いて `file://` で開き、computed style を読むだけで足りる(実測: 4〜6分)。

```bash
# 1) 配信される最終 HTML を実体化(バンドル込みの本物を出す。ソースの CSS を読むだけでは
#    ホスト変数のフォールバックが解決されず、実際に当たる色が分からない)
bun -e 'import {AGENDA_APP_HTML} from "/絶対パス/ui/agenda-app.ts"; await Bun.write("/絶対パス/out.html", AGENDA_APP_HTML)'
# 2) chrome-devtools MCP で file:// を開く → emulate(colorScheme: dark / light)
# 3) evaluate_script で **実 DOM 要素**の getComputedStyle を読み、WCAG 比を計算
```

### 🔴 監査のチェックリスト(A/B で「見落とし」が出た観点)

**色の値を見るだけでは足りない。変数が本当に代入されているかまで見る。**

| 確認 | なぜ見落とすか | 具体的な確かめ方 |
|---|---|---|
| **ホスト注入変数が `setProperty` されているか** | `var(--x, fallback)` は**参照があっても値が届いていなければ常にフォールバック**。CSS を読むだけでは「受け取る準備がある」ようにしか見えない | **配信されるバンドルまで** `setProperty("--` を grep し、実際に代入されているキーを列挙する。ホスト側が送るキー一覧と突き合わせる |
| **`var(--x)` の `--x` が定義されているか** | 名前の綴り違いは**エラーにならず静かにフォールバックする**。画面は「それらしく」出るので気づけない | `var(--` で参照されている全変数名を抽出し、**定義側(`--x:`)と集合の差を取る**。似た名前が別にあれば綴り違いを疑う |
| **逆向きも見る: 定義されているのに一度も参照されない変数はないか** | 上と同じ集合の差を**逆に取るだけ**なのに見落としやすい。**実装漏れ**(モックにはあった演出が実装に無い)か、**撤去し忘れ**のどちらか | 差を逆向き(`定義 − 参照`)にも取る。出たら**モック/デザイン資料を検索**して、本来どう使うはずだったかを確かめる |
| **light と dark の値を**並べて**極性を検算したか** | 個々の値が妥当でも、**light と dark を取り違えて入れている**ことがある。1トークンだけ逆でも他が正しいと目視では気づけない | 全トークンの light/dark を並べ、**文字色系は「light の方が暗い」が成り立つか**を機械的に検算する(成り立たないトークンだけ拾う) |
| **同じトークンを「文字色」と「塗り」の両方に使っていないか** | 暗地向けに**明るく**振ったトークンを塗りに使うと、その上に固定した白文字が**ダークだけ**失格する。ライトで通っていたので見逃す | `background: var(--X)` と `color: #fff` が同居する規則を洗い、`--X` の light/dark 両方の値で比を出す |
| **ライトも測ったか** | 「ダークが読みにくい」は**体感**であって測定ではない。実際はライトの方が悪いことがある | 両モードを同じスクリプトで測り、**トークンごとに並べる**(片方だけ測ると原因を取り違える) |
| **主役でない小さい文字を測ったか** | 11px 級の補助テキスト(最終更新・単位・プレースホルダ)は**見出しより低コントラストに設計されがち**で、しかも小さいので実害が大きい | フォントサイズの小さい規則を先に洗う |

> **Why not ここに実測値を書かないか(2026-08-02)**: 以前この表には具体的な数値と変数名を
> **実例として書いていた**。その結果、これを読んだエージェントは**測る前に答えを知っている**状態になり、
> 対応する eval が「発見できるか」ではなく「**思い出せるか**」の測定に変わってしまった
> (実行エージェント自身がこの汚染を申告した)。
> **所見をスキルに書き戻すときは「答え」ではなく「探し方」を書く。**
> 答えが要るなら、それは eval の記録(`evals/`)か、そのプロジェクトの課題管理に置く。

### ⚠️ 計測そのものの罠

- 🔴 **セレクタ検証のために単独要素を生成すると、子孫セレクタ(`.a .b`)が親を持たず継承値になる。**
  その数値は**信用してはいけない**。実際のカードを描画し、**本物の要素**の computed style を読む
  (この罠は実測で踏まれ、報告者自身が「これらの数値は信用せず取り直した」と申告している)。
- **ミニファイ済みバンドル**(`*-bundle.ts`)を grep すると出力が溢れる。**entry / app のソースに絞る。**
- スクリプトを scratchpad に置くと**相対 import が解決できない**。絶対パス import にする。
- ブラウザ MCP の `take_screenshot` は **workspace root 外の `filePath` を拒否する**ことがある。
  その場合は `filePath` を外してインラインで受け取る。
- zsh では `grep --include=*.swift` の**グロブが展開エラー**になる。クォートする。

> **Why not これを SKILL.md 本体に置かないか**: 監査は「WebView の中身を見る」タスクでしか要らず、
> Simulator 操作の大半には関係ない。**踏むと決まったときだけ開けばよい。**

## ブラウザに移せない「残り 2 割」(いずれも推論・要 Simulator/実機)

1. **WKWebView 固有の描画差**。shim は Chrome で動くので WebKit ではない。
   フォントレンダリング・flexbox/grid の際どい差・`backdrop-filter` 等は再現しない。
2. **ネイティブのジェスチャ排他バンド、セーフエリアの実物理値、WebView の高さ制約**。
3. **ホスト⇄WebView の実 JS ブリッジの実配線**(呼び出しが本当にサーバーまで届き、
   正しい権限で実行され、応答が戻る一連)。ただしこれも**ブラウザで完結する別経路**
   (実ホストの Inspector 等)でカバーできることが多い。
4. **表示モード遷移で WebView が document を再生成する**といったホスト実装依存の挙動。
5. **iOS のソフトキーボード**に依存する編集位置の問題(デスクトップ Chrome には仮想キーボードが無く
   原理的に再現できない)。

→ **この 2 割を潰すことに時間を使うより、WebView 側をホスト非依存に保つ設計努力の方が
レバレッジが大きい**、というのが track4 の結論。

タップで作らずに外から注入する。** 座標も IME も HID も一切関与しないので、
このスキルのハマりどころが**構造的に発生しない**。

## 1. 起動時の環境変数注入 — `SIMCTL_CHILD_*`(第一選択)

```bash
SIMCTL_CHILD_MYAPP_API_KEY="$SOME_KEY" \
SIMCTL_CHILD_MYAPP_SPIKE=todos \
  xcrun simctl launch --terminate-running-process <UDID> <bundle-id>
```

`SIMCTL_CHILD_` プレフィックスを外した名前が、起動されたアプリの
`ProcessInfo.processInfo.environment` に届く。**根拠は `xcrun simctl help launch` の最終行**
(「Any environment variables with the prefix SIMCTL_CHILD_ will be passed to the spawned process
with the prefix removed」相当の記述)。一次資料をその場で確認できる。

### 実測(track1)

| 項目 | 結果 |
|---|---|
| API キーを手入力ゼロでアプリへ渡せるか | ✅ 実測。実 LLM 往復(`PONG` が返る)まで確認 |
| 特定画面へ直行するフラグ(`SPIKE=transport`/`todos`) | ✅ 実測。いずれも **0 タップ** |
| UI 状態フラグ(サイドバー開)| ✅ 実測。**0 タップ** |
| 「チャットが打てる状態」への到達時間 | **2 秒・タップ 0**(旧来のタップ経路は数分+IME 化けの手戻り) |

### 設計側への含意(これが本題)

**アプリ側に env のエスケープハッチを仕込んでおくと、資格情報入力もログインも全部飛ばせる。**
自動操作の安定化を Simulator 側で頑張るより、**アプリに 5 行足す方が桁違いに効く**。

- 目的別に env を割る(`*_API_KEY` = 資格情報 / `*_SPIKE` = 到達画面 / `*_<FEATURE>_OPEN` = UI 状態)。
- **デバッグビルド限定にする**(本番に穴を残さない)。

### 落とし穴: 「効いているように見えて実はデッドコード」(track1 実測)

「起動時に自動接続する」env フラグが**実質デッドコードだった**という実例に当たった。
そのフラグを読むのは接続画面のコードだったが、アプリの既定ルートは別の画面で、
**その接続画面には遷移しない**。にもかかわらず「自動接続に成功した」ログは出ていた
—— env とは無関係に、後発の実装が常に自動接続する既定挙動になっていたためである。
**env のおかげだと誤認していた。**

→ **env フラグを「効いた」と判定するときは、A/B(フラグを外して同じ結果にならないこと)を取るか、
最低でもコードを読んでその env が読まれる経路に到達していることを確認する。**
「期待どおりの結果が出た」だけでは因果の証明にならない。

### URL スキームという別解

`xcrun simctl openurl <UDID> "myapp://add-server?name=x&url=..."` で
「フォームを開いてから入力する」経路そのものを飛ばせる。env が「起動時に1回」しか効かないのに対し、
URL スキームは**起動後に何度でも**撃てるのが利点。ただしアプリ側に `CFBundleURLTypes` +
`.onOpenURL` の実装が要る(track1 の対象アプリには無く、**入口ゼロ**だった)。

システム側の URL スキームは実装なしで使える。実測で有用だったもの:

```bash
xcrun simctl openurl <UDID> "App-prefs:root=General"   # 設定アプリの「一般」へ直行(タップ 0)

# ★ 照会カレンダーの購読シートを、URL が埋まった状態で開く(§4 の「温め」の要)
xcrun simctl openurl <UDID> 'webcal://<公開 ics の URL>'
#   ⚠️ 起動に時間がかかる。直後4秒はまだホーム画面(✅実測)。10 秒待つこと
```

⚠️ **`App-prefs:` で行ける先は限られる。** iOS 26 の「設定 → アプリ → カレンダー」配下への
ディープリンクは見つかっていない(`App-prefs:root=APPS` は無効 / `prefs:root=MOBILECAL` は
`code=115`)。→ 実測表は §4 の「ディープリンクが無い」。

## 2. `simctl clone` — 「一度手で作った状態」をバイト単位で量産する

env で渡せないもの(Keychain に入ってしまう資格情報、OS 側のアカウント DB、外観設定)は、
**一度だけ手で作って clone で運ぶ**のが現実解。

```bash
# ★ ソースは Shutdown 必須(実測)
xcrun simctl clone <SRC-UDID> "MyGolden-A"
# => code=405: Unable to clone device in current state: Booted   ← booted のままだと即エラー

SEED=<種のUDID>
xcrun simctl shutdown "$SEED"
NEW=$(xcrun simctl clone "$SEED" "MyGolden-A")   # 新 UDID が stdout に返る
xcrun simctl bootstatus "$NEW" -b                # ★ boot + 「起動完了まで待つ」を1コマンドで
```

### ✅実測: 所要時間は **合計 16.7 秒・0タップ**(2026-08-01 第3ラウンド)

| 工程 | 実測 |
|---|---|
| `xcrun simctl shutdown <SEED>` | **1.8 s** |
| `xcrun simctl clone <SEED> "<新名>"` | **4.8 s** |
| `xcrun simctl bootstatus <新UDID> -b` | **10.1 s** |
| **合計** | **16.7 s / タップ 0** |

> 💡 **`xcrun simctl bootstatus <UDID> -b` は boot と「起動完了まで待つ」を1コマンドでやる(✅実測)。**
> 固定 `sleep` が一切要らない。**プロビジョニングスクリプトの `boot` + `sleep 20` は
> 全部これに置き換えられる**(sleep は短すぎれば壊れ、長すぎれば遅い。どちらの調整も不要になる)。

### ✅実測: 運んだ状態が「実際に機能する」ところまで確認済み

「バイト単位で同一」は下の忠実度表のとおり第1ラウンドで取ってあるが、
第3ラウンドで **clone した端末が本当に動く**ことまで確認した:

- clone を boot → **リマインダー App を開いたら本番サーバーのリストが降ってきた**
  (`Tasks` 5件 / `reading list` 5件)。**Keychain のパスワードが復号されて実際に認証に使われている。**
- Proxyman の root CA(`simctl keychain add-root-cert` で入れたもの)も運ばれる
  → **clone 側で CA を入れ直す必要は無い**(✅実測。TLS が通って同期できたことが証拠)。

→ clone の評価は「DB の行がコピーされる」ではなく **「その端末はそのまま働ける」**。

### 忠実度(track3・すべて実測)

| 運ばれるもの | 結果 | 確認方法 |
|---|---|---|
| インストール済みアプリ | ✅ | clone 先の `simctl listapps` にヒット |
| UserDefaults(値まで) | ✅ | plist の中身が一致 |
| **Keychain** | ✅ **バイト単位で同一** | `keychain-2-debug.db` / `-wal` / `-shm` の SHA-256 が完全一致 |
| Keychain を**アプリが実際に復号して読めるか** | ✅ | clone を起動 → 設定画面の API キー欄が「入力済み」表示 |
| `Accounts3.sqlite` | ✅ バイト単位で同一 | SHA-256 一致 |
| 外観設定(ダークモード) | ✅ | `simctl ui appearance` で仕込んだマーカーが clone 先でも `dark` |

### 落とし穴

- **`xcrun simctl get_app_container <clone-UDID> <bundle> data` は clone 直後、
  コピー元デバイスのパスを返し続ける**(何度リトライしても同じ・実測)。実ファイルは
  `.../Devices/<clone-UDID>/data/Containers/Data/Application/<同じコンテナ UUID>/...` に
  ちゃんと存在するので、**`get_app_container` を信用せず直接パスを組み立てる**。
- clone 直後に出た警告アイコンを「Keychain が壊れた」と疑ったが、ログを読むと
  **TLS ハンドシェイクのタイムアウト**だった(ネットワークスタック初期化の一過性の遅延・推論)。
  **表面症状だけで「clone がデータを壊した」と即断しない。**
- 「認証切れバッジ」のような状態はコピー元にも元からあった。
  **目印を仕込む前に「それは事前に生きている状態か」を確認する**(track3 の反省)。

### 運用上の弱点

clone は「既存デバイスの複製」なので、量産のたびに**種を shutdown する**運用になる。
バージョン管理もできない(バイナリの塊)。**冪等性・差分レビューが要るものは次の
`.mobileconfig` の方が筋が良い** —— ただし **アカウント系ペイロードは `.mobileconfig` では
そもそも効かない**ことが実測で確定した(§3)。**アカウントを運ぶ手段は clone 一択。**

## 3. `.mobileconfig` — 構成プロファイルを CLI から流し込む

`xcrun simctl` に構成プロファイル専用のサブコマンドは**無い**(グローバルフラグの
`--profiles <path>` はデバイス"型"定義用で、構成プロファイルとは無関係。track3 で確認済み)。

しかし **`openurl` に `file://` を渡すと Safari のプロファイル DL フローが起動する**(実測)。
**HTTP サーバーを立てる必要も、ドラッグ&ドロップも要らない。**

```bash
mkdir -p ~/tmp-sim && cp your.mobileconfig ~/tmp-sim/
xcrun simctl openurl <UDID> "file://$HOME/tmp-sim/your.mobileconfig"
# → Safari:「このWebサイトは構成プロファイルをダウンロードしようとしています」→ 許可(タップ1)
# → 「プロファイルがダウンロードされました」→ 閉じる(タップ2)

xcrun simctl openurl <UDID> "App-prefs:root=General"
# → 設定アプリの「一般」へ直行(タップ 0)。「ダウンロード済みのプロファイル」が一覧最上部に出る
# → タップ(3)→ インストール(4)→ 未署名警告のインストール(5)→ 最終確認の赤いインストール(6)
```

**合計 6 タップでインストール完了(実測)。** 手入力での CalDAV アカウント追加は約 20 タップ
(うち手入力3箇所)なので、タップ数も IME 事故の面数も大幅に減る。
プロファイルは XML なので **git で差分レビューでき、冪等に再適用できる**のも clone に対する利点。

### 🔴 実測: アカウントは**作られなかった**(この経路は現時点で使えない)

**インストールは「インストール完了」まで到達するのに、`Accounts3.sqlite` にアカウント行が
増えない。** これはダミーホストでも実サーバーでも同じだった。

| 試行 | ホスト | 認証 | インストール | `Accounts3.sqlite` |
|---|---|---|---|---|
| 1回目 | 到達不能なダミー | ダミー | ✅ 完了 | ❌ 3行のまま(増えず) |
| 2回目 | 実サーバー(Cloud Run) | **実認証・curl で検証済み** | ✅ 完了 | ❌ 3行のまま(増えず) |

2回目は事前に `curl` で **Basic 認証が通ること・DAV ヘッダが返ること・`principal-URL` と
`calendar-home-set` が解決すること**まで確認してから実施している。**サーバー側の問題ではない。**

#### ★ここでも誤診をした(記録として残す)

1回目のあと、ログに出ていた `The connection to ACDAccountStore was invalidated.` を
「accountsd が検証に失敗してアカウント作成を中断した証拠」と解釈し、
**「実認証情報なら通るはず」という推論を立てた。この推論は外れた。**

再調査でわかったこと:

- この行は **accountsd のすべての XPC クライアント**(`profiled` / `cloudd` / `Preferences` /
  `icloudmailagent`)に対して同じように出る。**接続の後始末のノイズであって、
  CalDAV 固有のエラーではない。**
- 45 秒のウィンドウでユニファイドログをホスト名で grep しても **ヒット 0**。
  つまり **accountsd はサーバーに接続を試みてすらいない。**
- `ZACCOUNTTYPE` に `com.apple.account.CalDAV` は**登録されている**
  (= 「Simulator にアカウント型が無い」ではない)。

→ 「筋の通ったログの読み」を検証せずに事実として扱った、という **SKILL.md「診断の規律」
そのものの実例**。同じ日にこれで3回転んでいる。

#### 現時点の推論と、決着させるための実験

**推論(未確証)**: プロファイル起点の CalDAV アカウント作成が、iOS Simulator では
最後まで結線されていない可能性がある。認証情報の真偽とは無関係。

**決着させるには、まず対照実験を1本やる**:

> **設定アプリから手入力で**同じサーバーの CalDAV アカウントを追加し、
> `Accounts3.sqlite` に行が立つか。
>
> - 立つ → `.mobileconfig` 経路**固有**の問題。手入力 → `simctl clone` で量産すればよい
>   (clone は `Accounts3.sqlite` をバイト単位で運ぶことが実測済み。§2 参照)
> - 立たない → **Simulator では CalDAV アカウントを作れない**。実機に寄せるしかない

> **2026-08-01 第2ラウンドで実施した(→ §4)。結果は「立つ」側。**
> 設定アプリからの手入力なら(§4 の「追加 → 保存 → 削除 → 追加」の儀式を踏めば)
> **CalDAV アカウントは成立し、カレンダー/リマインダーのデータクラスも ON にできる**。
> つまり **「Simulator では CalDAV アカウントを作れない」ではない。**
> `.mobileconfig` 経路が空振りする理由は依然として未解明のまま残る。
> **(→ 第3ラウンドで「アカウント系ペイロード全般が作らない」まで詰めた。直下の撤回節を見よ。
> なお §4 の『儀式』自体も第3ラウンドで不要になっている。)**
>
> ※ **`Accounts3.sqlite` を直接 `sqlite3` で数えて裏を取っている**(実測)。
> 手入力で成立した端末では、ベースライン2行(`local` / 日本の祝日)に対して
> **CalDAV の行が増え `ZACTIVE=1`**、`Z_2ENABLEDDATACLASSES` に
> **そのアカウントのデータクラスが2件**紐付いていた。
> 一方 `.mobileconfig` 経路では、インストール完了まで到達しても
> **行数が一切変わらなかった**(ダミーホストでも実サーバーでも同じ)。
> 「UI で成立して見える/見えない」ではなく **DB の実データで対比している**ので、
> この判定は表示の遅れなどでは説明できない。
>
> ```bash
> sqlite3 ~/Library/Developer/CoreSimulator/Devices/<UDID>/data/Library/Accounts/Accounts3.sqlite \
>   "SELECT Z_PK, ZACCOUNTDESCRIPTION, ZUSERNAME, ZACTIVE FROM ZACCOUNT;"
> sqlite3 ... "SELECT * FROM Z_2ENABLEDDATACLASSES;"   # 左が account の Z_PK
> ```

→ **この経路を「アカウント投入の手段」として使わないこと(第3ラウンドで確定・下記)。**
`.mobileconfig` 自体は Wi-Fi・証明書・制限など他のペイロードでは有効(と期待される)なので、
「構成プロファイルを CLI から流し込める」という配送経路の実測(6タップ)は生きている。

### ❌ 撤回(2026-08-01 第3ラウンド): 「温めれば通る」説は**実測で否定された**

> **【撤回前の記述(第2ラウンド時点の推論)】**
> 「`.mobileconfig` を試した端末はどちらも**まっさらな新品**だった。§4 で判明した
> 『ユーザー追加アカウントがゼロの端末では CalDAV アカウントの初回追加が失敗する』現象と
> **同じ根**(端末内キャッシュの欠如)かもしれない。§4 の手順で CalDAV アカウントを1つ
> 成立させた端末に同じ `.mobileconfig` を流せば行が立つのではないか。」
>
> **→ その検証を第3ラウンドで実施した。行は立たなかった。この推論は❌否定された。**

#### 実験1: **温かい端末**に CalDAV ペイロードを流した → ❌ 行は増えない(✅実測)

対象は **CalDAV アカウントが1つ成立済み + 照会カレンダーもある**端末(§4 の意味で十分に温かい)。
プロファイルは実サーバー(Cloud Run 側。既存アカウントとは**別ホスト**)。

| | 実測 |
|---|---|
| インストール UI | ✅「インストール完了」まで到達 |
| `Accounts3.sqlite`(前) | 4 行 |
| `Accounts3.sqlite`(後・+20 秒待ち含む) | **4 行のまま。増えない** |

#### 実験2: **認証すら不要な照会カレンダーのペイロード**でも作られない(✅実測・新知見)

切り分けとして、`com.apple.subscribedcalendar.account`(= サーバー認証も要らない、
最も単純なアカウントペイロード)**だけ**を含むプロファイルを新品端末に入れた:

| | 実測 |
|---|---|
| インストール UI | ✅「インストール完了」。内容欄に「照会カレンダー」と正しく表示された |
| `Accounts3.sqlite` | **2 行のまま。増えない** |

**同じ購読を `webcal://` から手で入れれば行は立つ(§4)。**
→ **ペイロードの記述ミスではなく、プロファイル経路がアカウントを作らない。**

#### 更新後の結論(✅実測)

> **iOS Simulator では、アカウント系ペイロード全般がアカウントを作らない。
> 端末の温度とは無関係で、CalDAV 固有ですらない。**

- 🔶 **推論**: `profiled` → `accountsd` のアカウント作成経路が Simulator では結線されていない。
  (`ZACCOUNTTYPE` に型自体は登録されている = 「型が無い」ではない、という第2ラウンドの観測と整合)
- ❓ **未検証**: Wi-Fi・証明書・制限といった**非アカウント系**ペイロードが効くか。
  第3ラウンドでは「アカウント系だけが駄目」を**2種類のアカウントペイロード**で示す方を選んだ
  (そちらの方が切り分けの情報量が大きいと判断した)。
- 誤診の解剖(なぜこの推論に筋が通って見えたか)は `retracted-2026-08-01.md` §12。

### 💡 `.mobileconfig` の適用判定は UI ではなくプロファイルストアで取る(✅実測)

「インストール完了」の表示は**配送が成功した**ことしか意味しない。
配送とペイロード適用を分けて観測するには、OS 側のプロファイルストアを直接見る:

```
~/Library/Developer/CoreSimulator/Devices/<UDID>/data/Containers/Shared/SystemGroup/
  systemgroup.com.apple.configurationprofiles/Library/ConfigurationProfiles/
    ├─ profile-<sha256>.stub   ← プロファイル実体
    ├─ ProfileTruth.plist      ← "<PayloadIdentifier>" => {...} が登録されていれば配送成功
    ├─ PayloadManifest.plist   ← OrderedProfiles に載る
    └─ MCProfileEvents.plist   ← Operation=install / Process=com.apple.Preferences
```

第3ラウンドではこの4つが**すべて正常に更新されていた**のに `Accounts3.sqlite` は不変だった。
→ **「配送は成功しているのにペイロードが効いていない」を一発で切り分けられる。**
`.mobileconfig` がらみで詰まったら、UI ではなくここと `Accounts3.sqlite` の**両方**を見る。

## 4. 🔴 CalDAV アカウント — まっさらな端末では初回追加が**必ず**失敗する(**回避策は確定済み**)

**2026-08-01 第2ラウンドの実測。** §3 の対照実験(「手入力なら成立するのか」)を決着させに行った
ところ、**本題より先に、Simulator 特有の障害を1つ掘り当てた。** ここを知らないと
「自分のサーバーが悪い」と誤診してサーバー側を延々デバッグすることになる。

> **✅ 先に結論(2026-08-01 第3ラウンドで確定)**
>
> **`webcal://` で照会カレンダーを1つ入れてから CalDAV を追加すれば、初回から通る(✅実測)。**
> **4タップ・テキスト入力ゼロ**で温まり、CalDAV は**1回目でトグル一覧が出る**。
> **第2ラウンドで書いていた「追加 → 保存 → 削除 → 追加」の儀式はもう要らない。**
>
> 症状そのもの(まっさらだと初回が失敗する)は**そのまま生きている**。
> 変わったのは**払うコスト**だけ、というのがこの節の読み方。

### 症状(実測)

**ユーザー追加アカウントが1つも無い** Simulator で、

> 設定 → アプリ → カレンダー → アカウント → アカウントを追加 → その他 → CalDAVアカウント

を実行し、サーバー・ユーザ名・パスワードを入れて「次へ」を押すと:

- **サーバー検証は成功する**(accountsd のログに `Authenticator determined credentials are valid`)
- **なのに、次の画面に出るべき「カレンダー/リマインダー」のトグル一覧が空**
- そのまま保存すると **データクラス0個 = 「停止中」と表示されるアカウント**ができる

### ✅ 回避策(**推奨・第3ラウンドの実測で確定**): `webcal://` で先に照会カレンダーを1つ入れる

**第2ラウンドではこれを「未検証の有望な回避策」として書いていた。第3ラウンドで実測し、
通ることを確認したので推奨手順に格上げする。**(着想の出典は本節末尾に残してある)

```bash
U=<UDID>
xcrun simctl openurl "$U" \
  'webcal://calendar.google.com/calendar/ical/ja.japanese%23holiday%40group.v.calendar.google.com/public/basic.ics'
sleep 10     # ★ 4秒ではまだホーム画面。下の罠1を見よ
```

- ✅ カレンダー App が起動し、**照会 URL が埋まった状態で**「照会カレンダーを追加」シートが出る。
  **URL の手入力は一切不要**(= IME 化けの面数がゼロ)。
- ✅ `%23` / `%40` を含む URL を `openurl` にそのまま渡して壊れない(実測)。
- タップは **4回だけ**(points):
  1. 「許可しない」(通知の許可) ← カレンダー App 初回起動時のみ
  2. 「許可しない」(位置情報の許可) ← 同上
  3. 「検索」(例: 201, 404)← フィードを解決し、プレビューが出る
  4. **赤い ✓ ボタン**(例: 363, 110)← ここで購読が確定

確認(✅実測・`Accounts3.sqlite` に行が立つ):

```
3|SubscribedCalendar||日本の祝日|3A2EE920-...    ← 新規に立った行
```

**この状態で CalDAV アカウントを追加すると、1回目でトグル一覧が出る(✅実測)**:

```
'カレンダー'   | CheckBox | '1'    ← 1回目で出た
'リマインダー' | CheckBox | '1'
保存後: Z_2ENABLEDDATACLASSES に 22(カレンダー)/ 5(リマインダー)の2件
```

**「追加 → 保存 → 削除 → 追加」の儀式は一度も踏んでいない。一発で成立した。**

#### ⚠️ この経路の罠(2つとも実測。知らないと必ず詰まる)

1. **`openurl webcal://` の直後4秒はまだホーム画面。** カレンダー App の起動待ちで、
   そこでスクショを撮ると「効かなかった」に見える。**10 秒待つ。**
   (`idb ui tap` の無言の失敗と**同じ誤診構造** —— 観測が早すぎるだけ)
2. 🔴 **購読確定の赤い ✓ ボタンが `idb ui describe-all` に出てこない(✅実測)。**
   AX 走査だけを見ていると「追加ボタンが無い」と誤診する。
   **スクショで座標を取るしかない**(pt = px ÷ scale。1206x2622 px はスケール3で 402x874 pt)。
   → **`describe-all` を唯一の真実にしてはいけない**、という一般則の実例。

### ⛔ 旧回避策(第2ラウンド): 「追加 → 保存 → 削除 → 追加」の儀式 — **もう不要**

**記録として残す**(消さない方針)。上の webcal 前置きが使えない事情があるときの代替:

1. **1回目を「保存」まで進める。**(トグルが空でも構わない)
2. **できた「停止中」アカウントを削除する。**
3. **もう一度、同じ手順で追加する。→ 今度はトグル一覧が出る。**

**⚠️ キャンセルでは駄目。「保存」まで到達させる必要がある(実測)。**
一度どれか1つ CalDAV アカウントが成立した端末では、**別ホストの2つ目以降は1回目から成功する。**

⛔ ただし **タップ約30回・テキスト入力6回・削除操作つき**で、webcal 前置き(4タップ・入力0)より
明確に高くつき、削除を挟むぶん壊れやすい。**第一選択にはしない。**

### 対照実験(すべて新規作成した端末・実測)

| 条件 | 1回目でトグルが出るか |
|---|---|
| 新品 + 自作サーバー(Cloudflare Workers) | ❌ |
| 新品 + 同上(事前にリマインダー/カレンダー App を起動して**温めた**) | ❌ |
| 新品 + 別ホスト(Cloud Run。`:8443` に応答しない入口) | ❌ |
| **新品 + 完全に無関係な他社 CalDAV サーバー(Vikunja のデモ)** | ❌ |
| **既に CalDAV アカウントが1つある端末** + 別ホスト | ✅ |
| ✅ **新品 + `webcal://` の照会カレンダーを1つ入れた端末**(第3ラウンド) | ✅ **出た** |

**他社サーバーでも再現する = サーバー実装とは無関係の iOS 側の挙動。**
「自分のサーバーの RFC 準拠が足りない」という方向へ舵を切らないこと。

### 根拠となる観測(なぜ「サーバーは関係ない」と言えるか)

1. **両試行がサーバーへ送るリクエストは 6 件でバイト単位に同一(実測)。**
   `.well-known/caldav` → `/dav/` → `OPTIONS {principal}` を、**443 と 8443 の2経路ぶん**。
   → **2回目はサーバーに追加の問い合わせを一切していない。**
   つまり2回目の成功を支えている判断材料は**端末内のキャッシュ**から来ている。
2. **両試行ともサーバーの応答は同じ**(301 / 207 / 204)。accountsd のログにも
   `Authenticator determined credentials are valid` が出る。**検証は通っている。**
3. **検証成功の 1.00 秒後に ACUI が自動保存を走らせる**(5回中4回で 1.003〜1.009s・実測)。
   **トグル画面はその保存の後に出る。** → 「保存すると停止中になる」は独立した障害ではなく、
   **トグルを1つも ON にせずこの画面を抜けた正常な結果**にすぎない。
4. **成功時にだけ `com.apple.accounts.dom`**(accountsd のデータクラス所有者ヘルパ)
   **が remindd を起動している**(`AAACCOUNTS` を含む LAUNCH EVENT)。観測5件で **5/5 一致**。
   → 「どのデータクラスを提供できるか」を答える所有者プロセスが、1回目には出てこない。
5. **RFC 6764 §6** は、クライアントは **successfully used** した接続情報(scheme/host/port 込み)を
   キャッシュして再利用**すべき**、と規定している。「保存しないと2回目が通らない」
   (キャンセルでは駄目)はこれと符合する —— **保存 = successfully used** と読める。

> **推論(未検証)**: 1〜5 を素直につなぐと「初回はデータクラス所有者の解決に必要な
> 端末内キャッシュ(接続情報 or アカウント型の所有者マップ)が無く、その解決を待たずに
> トグル画面が構築されてしまう」という筋になる。**ただしこれは推論。**
> 5 の RFC 6764 は「保存が要る」ことの説明にはなるが、**「初回にトグルが出ない」ことの
> 直接の証拠ではない**(1回目も 2回目も同じ 6 リクエストを実際に送って成功している)。
>
> **第3ラウンドで絞り込めた点(✅実測)**: **接続先を一切共有しない `SubscribedCalendar` で
> 温まる**以上、**RFC 6764 の「successfully used な接続情報のキャッシュ」では説明できない。**
> 括弧内の2択のうち「接続情報」側は落ちた。残っているのは
> **「アカウント型の所有者マップ」ないしホスト非依存の一度きりの初期化**の側。
> ただし**どちらであるかの直接証拠はまだ無い**(🔶推論のまま)。

### なぜ今まで気づかなかったか

**iOS 挙動の検証は従来ずっと実機でやっていた。** 実機には Apple ID やメールのアカウントが
既にあるので「**ユーザー追加アカウントがゼロ**」の状態にならず、この現象に当たらない。
**まっさらな Simulator 特有の罠。** 実機で通っている手順書をそのまま Simulator に持ち込むと踏む。

### ✅ 何が「温める」のか — **ユーザーが追加したアカウントが1つあればよい。型は問わない**

第3ラウンドで、この節でいちばん曖昧だった点に**実測で答えが出た**。

**(a) 「CalDAV アカウントでなければ温まらない」は❌否定された。**
温めたのは `SubscribedCalendar`(照会カレンダー)であって、**CalDAV とは `ZACCOUNTTYPE` が別**。
アカウント型が違っても温まる。
→ **条件は「CalDAV アカウント型が成立していること」ではなく「ユーザー追加アカウントが1つ以上ある」こと。**

**(b) 「システムアカウントは数に入らない」が推論から✅実測に格上げされた。**
webcal で温めた端末の `Accounts3.sqlite` には **「日本の祝日」の行が2つ並ぶ**:

| 行 | 由来 | 温めたか |
|---|---|---|
| `HolidayCalDaemonAccount` | 新品端末に最初から入っているシステム管理のデーモンアカウント | ❌ **温めない** |
| `SubscribedCalendar`(`webcal://` で追加) | **ユーザーが追加した**照会カレンダー | ✅ **これが温めた** |

**同じ端末に、同じ名前("日本の祝日")の行が、片方は無力・片方は有効な状態で共存している。**
表示名が同じなので、UI だけを見ていると「アカウントはもう1つあるのに再現する」と混乱する。
**判定は必ず `ZACCOUNTTYPE` を JOIN して見る**(下の確認コマンド参照)。

⚠️ 同様に、**リマインダー/カレンダー App を先に起動して温めても効かない**
(→ `retracted-2026-08-01.md` §11)。「App が起動している」は accountsd から見た状態ではない。

❓ **未検証**: メール等、`SubscribedCalendar` 以外の型でも温まるか。
今回は「型が違っても温まる」ことを 1 例で示した段階(= 「CalDAV 限定」説の反証としては十分だが、
「どんな型でもよい」の証明にはなっていない)。

> 💡 **この実測は、`docs/modeling/06` 側に残っていた未解決論点にも答えを与える** ——
> 「RFC 6764 のホスト単位キャッシュでは説明できない、ホスト非依存の一度きりのウォームアップ」が
> 疑われていたが、**ホストどころかアカウント型にすら依存しない**ことが示された。
> 温まりの単位は「接続先」ではなく **「この端末にユーザー追加アカウントが存在するか」**。

### ★★ 推奨手順: まっさらから「CalDAV アカウント入り Simulator」を用意する(2段構え)

**第3ラウンドの実測でこの手順に確定した。** 段を分けるのが要点 ——
**手作業は「種を1台作る」ときの1回だけ**で、以後は**何台でも 0タップ**。

#### 一度だけ: 種(seed)を作る(✅実測 ~4 分 / 約15タップ / テキスト入力3箇所)

```bash
# 1) 端末を作って boot(実測 ~40 s)。★ bootstatus なら固定 sleep が要らない
U=$(xcrun simctl create "CalDAV-Seed-$(date +%m%d)" \
      com.apple.CoreSimulator.SimDeviceType.iPhone-17 \
      com.apple.CoreSimulator.SimRuntime.iOS-26-4)
xcrun simctl bootstatus "$U" -b

# 2) ★ システムプロキシが有効なら CA を入れる(入れないと TLS が全部落ちる → SKILL.md 事前チェック4)
networksetup -getsecurewebproxy "Wi-Fi"          # Enabled: Yes なら↓は必須
xcrun simctl keychain "$U" add-root-cert \
  "$HOME/Library/Application Support/com.proxyman.NSProxy/app-data/proxyman-ca.pem"

# 3) ★★ 照会カレンダーで「温める」(4タップ・テキスト入力0)
xcrun simctl openurl "$U" \
  'webcal://calendar.google.com/calendar/ical/ja.japanese%23holiday%40group.v.calendar.google.com/public/basic.ics'
sleep 10        # ★ 4秒ではまだホーム画面
#   → 「許可しない」×2(通知/位置情報。カレンダー App の初回起動時のみ)
#   → 「検索」→ **赤い ✓**(★ describe-all に出ない。スクショで座標を取る)

# 4) CalDAV を追加(★ 儀式は不要。1回目でトグルが出る)
xcrun simctl openurl "$U" "App-prefs:root=General"
#   設定root →(下へスクロール)アプリ → カレンダー → カレンダーアカウント
#     → アカウントを追加 → その他のアカウントを追加… → CalDAVアカウント
#   ⚠️ ここへのディープリンクは無い(下の「ディープリンクが無い」を見よ)。スクロール+タップで行く
#   サーバ/ユーザ名/パスワード欄は IME 化けに注意(Caps Lock か pbcopy。SKILL.md「テキスト入力」)

# 5) ★ 判定は UI ではなく DB で。ZACCOUNTTYPE を JOIN しないと「日本の祝日」2行に騙される
sqlite3 ~/Library/Developer/CoreSimulator/Devices/$U/data/Library/Accounts/Accounts3.sqlite \
  "SELECT a.Z_PK, t.ZACCOUNTTYPEDESCRIPTION, a.ZUSERNAME, a.ZACCOUNTDESCRIPTION, a.ZACTIVE
     FROM ZACCOUNT a LEFT JOIN ZACCOUNTTYPE t ON a.ZACCOUNTTYPE = t.Z_PK;"
sqlite3 ... "SELECT * FROM Z_2ENABLEDDATACLASSES;"   # CalDAV の Z_PK に 22 と 5 が付けば成功

# 6) 種として保存: shutdown しておく(clone はソースが Shutdown 必須)
xcrun simctl shutdown "$U"
```

#### 以後: 何台でも clone する(✅実測 **16.7 秒・0タップ**)

```bash
SEED=<種のUDID>
xcrun simctl shutdown "$SEED"                        # 既に shutdown 済みなら no-op
NEW=$(xcrun simctl clone "$SEED" "CalDAV-Worker-01")
xcrun simctl bootstatus "$NEW" -b
echo "$NEW"
```

**要点: 手作業は種で1回だけ払う。** 以降は clone がアカウントごと運ぶので、
検証端末を何台作っても「初回追加が失敗する」問題を二度と踏まない。
**壊したら捨てて clone し直す**という運用にできるのが最大の利点(冪等な作り直し)。
✅ アカウント・Keychain・Proxyman CA が全部運ばれ、**同期が実際に動く**ところまで確認済み(§2)。

⚠️ 種の作成自体は依然として手作業で、**CLI だけでは完結していない**。
`.mobileconfig` が使えれば完全自動化できたが、それは §3 のとおり**アカウント系では不可**が確定した。

#### ⚠️ ディープリンクが無い(✅実測。ここは手で辿るしかない)

iOS 26 でアカウント設定が「設定 → アプリ → カレンダー」の下へ移った先に、直行する URL は**無い**:

| URL | 実測 |
|---|---|
| `App-prefs:root=General` | ✅ 効く(ただし「設定アプリを前面化する」だけ。既に別画面を出していれば**その画面のまま**) |
| `App-prefs:root=APPS` / `...&path=MOBILECAL` | ❌ 設定ルートに落ちるだけ |
| `prefs:root=MOBILECAL` | ❌ `LSApplicationWorkspaceErrorDomain code=115` |

→ **新品端末なら `App-prefs:root=General` で設定ルートに出る**ので、そこから手で辿る。
既に設定アプリが別画面にいるなら、先に戻るかホームへ落としてから撃つ。
(❓ 網羅的に試したわけではない。他に効く URL がある可能性は残る)

#### 種に名前を付けるときの助言

種は使い回すので、**名前で「何が入っているか」と「どう作ったか」が引けるようにする**。
`Probe-1` のような通し番号だと、数日後に自分でも中身が分からなくなる
(実地でそうなり、途中で全台リネームする羽目になった)。

- **入っているものを名前に入れる**(どのサービスのアカウントが成立しているか)
- **種と使い捨てを名前で区別する**(誤って種を汚さないため)
- 検証の証拠として残す端末は、**何を示す証拠なのかを名前に入れる**

### この回避策の出典(格上げの経緯を残す)

**着想の出典**: ユーザーが過去に Maestro でこの問題に当たったとき、
**追加が最も簡単な「照会カレンダー」を先に入れてから CalDAV を追加していた**という証言。
当時は「そういうものだ」と流していたが、この節の発見と符合したので仮説として書き留めた。

- **第2ラウンド**: 「未検証の有望な回避策」として記載(❓実測ではない、と明示)。
- **第3ラウンド**: そのとおり実行し、**✅実測で確定 → 推奨手順へ格上げ**(上記)。
  同時に**「CalDAV アカウント型の成立が条件」説が❌否定**され、
  条件は「ユーザー追加アカウントが1つ以上」だと分かった(= 通らなかった場合に得る予定だった
  情報とは逆側の結論が出た)。

**「そういうものだ」で流していた現場の勘が、そのまま当たった一件。**
仮説として書き留めておいたから検証できた —— 未検証の勘も、**未検証と明示した上で**残す価値がある。

落ちるなら、それはこの節の症状ではなくプロキシの症状。** 混同しないこと

### この結論に至るまでに外した仮説(6本 + 第3ラウンドで1本)

## 4-b. 検討して採らなかった経路(第3ラウンドで結論を出した2本)

§4 の推奨手順が **0タップ 16.7 秒**に落ちた結果、以下は**やる価値が下がった**。
「検討していない」ではなく「**検討して採らなかった**」ことを記録する。

### XCUITest で設定アプリの追加フローを自動化する → 🔶 **可能だが ROI が低い**

- **技術的には可能**: `XCUIApplication(bundleIdentifier: "com.apple.Preferences")` で
  システム App も普通に操作できる(XCUITest の標準機能)。**Simulator なら署名不要**
  (`CODE_SIGNING_ALLOWED=NO`)、**ホストアプリも不要**(Target Application 未設定の
  UI テストバンドルで成立する)。実行は `xcodebuild test -destination 'id=<UDID>'`。
- ❌ **それでも採らない理由**:
  1. **自動化して得するのは「種を作る」1回だけ。** 量産側は既に clone で 0タップ 16.7 秒。
  2. 🔴 **デバイスの所有権の衝突リスクを常設することになる**(SKILL.md「デバイスの所有権」)。
     `xcodebuild test` は同じ端末を掴んでいる `idb` セッションのアプリを落とす。
     **種作りのためだけに別リポジトリへテストターゲットを足し、事故の面を常設する**のは筋が悪い。
  3. パスワードを XCUITest のソース(または env 経由の配線)に置くことになる。
  4. ❓ **AX の穴が消える保証がない**: §4 の赤い ✓ は `describe-all` に出ない。XCUITest なら
     `boundBy:` や座標タップで回避できる**はず**だが未検証。「XCUITest にすれば解決」とは限らない。
- 🔶 **昇格条件**: 「サーバー側の変更のたびにアカウント設定をやり直して回帰を見る」ような
  **反復が実際に発生したら**検討する。それまでは不要。**実装はしていない。**

### `Accounts3.sqlite` を直接書く → ⛔ **やれるが勧めない(clone の劣化版)**

✅実測で分かった構造(CalDAV アカウント1件あたり):

```
ZACCOUNT:  ZACCOUNTTYPE=31 (= com.apple.account.CalDAV) / ZACTIVE=1 / ZAUTHENTICATED=1 /
           ZVISIBLE=1 / ZWARMINGUP=0 / ZOWNINGBUNDLEID='com.apple.Preferences' ほか
ZACCOUNTPROPERTY (ZOWNER=<Z_PK>) — 10 件。ZVALUE はすべて NSKeyedArchiver の bplist
           (DAAccountHost / DAAccountPort / DAAccountUseSSL / CalDAVPrincipals / …)
Z_2ENABLEDDATACLASSES: (<Z_PK>,22)=カレンダー / (<Z_PK>,5)=リマインダー
```

**足りないもの(これが決定打・✅実測)**:

- 🔴 **パスワードは `Accounts3.sqlite` に無い。** Keychain
  (`Library/Keychains/keychain-2-debug.db` の `inet` テーブル)にあり、**列が暗号化されている**
  (`sqlite3` で開いても `srvr`/`acct` すらバイナリ)。**DB だけ書いてもアカウントは認証できない。**
- **`CalDAVPrincipals` は 1342 バイトの bplist。** principal URL やサポート機能の解決結果が
  焼き込まれている(= サーバーと往復した結果のキャッシュ)。手で組むのは非現実的。
- 🔶 **推論**: `accountsd` はメモリ上にキャッシュを持つので、端末稼働中に DB を書き換えても
  反映されない見込み(今回は試していない)。

→ **Keychain ごと運ぶなら、それは `simctl clone` そのもの。** 直書きは clone の劣化版にしかならない。

## 5. 使い分けのまとめ

| 作りたい状態 | 第一選択 | 理由 |
|---|---|---|
| API キー・フィーチャフラグ・到達画面 | **env 注入** | 0 タップ・2 秒・アプリ側の実装コストも小さい |
| 起動後に何度も撃ちたい状態変更 | **URL スキーム** | env は起動時 1 回きり。ただしアプリ側の実装が要る |
| Keychain / OS 側アカウント / 外観など env で渡せないもの | **clone** | バイト単位の忠実度が実測済み(**16.7 秒・0タップ**)。ただし種の shutdown が要る |
| OS のアカウント設定(CalDAV 等) | **① `webcal://` で温めて種を1台作る → ② `clone` で量産**(§4) | 🔴 まっさらな端末は初回追加が必ず失敗するが、**`webcal://` の照会カレンダーを1つ入れておけば1回目から通る(✅実測。儀式は不要)**。温めるのに CalDAV 型である必要は**ない**(ユーザー追加アカウントが1つあればよい)。量産は clone(**16.7 秒・0タップ**)。⛔ `.mobileconfig` は**アカウント系ペイロード全般が効かない**ことを実測(§3)—— 温めても駄目。⛔ `Accounts3.sqlite` 直書きは Keychain が別なので clone の劣化版(§4-b) |
| Wi-Fi・証明書・制限など**非アカウント系**の設定 | **`.mobileconfig`**(❓効くかは未検証) | 配送経路は 6 タップで有効(✅実測)。XML なので git 差分レビュー可・冪等。**ただし実際に効くのを確認したのはアカウント系の「効かない」側だけ**(§3) |

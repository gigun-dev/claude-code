## 1. 「`recordVideo` 中にタップすると HID が死ぬ。`idb kill` では戻らず shutdown→boot が必要」

### そう信じられていた理由

長時間の画面収録をかけながら UI 操作を続けたセッションで、途中から `idb ui tap` が全て
無反応になった。**エラーは出ず exit 0 で返り、画面だけ変わらない**。同時に走っていたのが
`recordVideo` だったので「録画が HID を壊す」と結論した。復旧に `idb kill` → `idb connect` が
効かず、`shutdown`→`boot` で直ったので「HID(Simulator 側)が壊れた」という説明も付いた。
筋の通った物語だったが、**対照実験を一度も取っていなかった**。

### 実験で分かったこと(2026-08-01・track2)

同一デバイス上で、タップの成否を `idb ui describe-point` と
**`xcrun simctl io screenshot` のバイト比較(`cmp`)** の二重で判定する 20 タップ試験を3条件で実施:

| 条件 | 20 タップ中の失敗 | HID 死亡 |
|---|---|---|
| 録画なし(ベースライン) | 0 | No |
| **`simctl io recordVideo` 中** | **0** | **No** |
| `ffmpeg -f avfoundation` 録画中(0.6s 間隔) | 9 | 部分的 |
| `ffmpeg -f avfoundation` 録画中(1.5s 間隔) | 10 | ほぼ 100%(片方向) |

**`simctl` 録画中は 20/20 成功した。仮説は否定された。** しかも「録画に逃げ道を作るなら
ffmpeg だろう」という対案側の方が、圧倒的にタップを落とした(§4)。

### 何が本当の原因だったか(未確定・推論を含む)

- 確実に言えるのは「**元の観測が誤った作法で取られていた**」こと。旧手順は
  `pkill -f recordVideo` を撃って `sleep` するだけで、**録画プロセスの exit を待っていなかった**。
  停止したつもりで走り続けている録画と、その後の操作が重なっていた。
- 検証の終盤で「**録画と無関係に**タップが 5/5 効かなくなる」状態にも遭遇した(track2 §B-4)。
  引き金は (a) 直前の重い ffmpeg 負荷の後遺症 か (b) 短時間に 100 回以上タップした
  companion 側の累積劣化 か、**切り分けられていない(推論)**。
- つまり「HID がいずれスタックすることがある」という**現象自体は実在する**。誤っていたのは
  **その原因を `recordVideo` だと断定したこと**。

### 現在の正しい記述

- 「HID が死んだ」と判定する前に、**まず「対象アプリが前面にいるか」を疑う**(§3 参照)。
  前面にいないだけのケースが、実地では圧倒的に多い。
- 本当に HID がスタックしている(前面化しても `simctl io screenshot` のバイト比較で
  画面が変わらない)なら、`shutdown`→`boot`→`idb connect` は依然として有効な最終手段。
  **ただしそれは「録画のせい」ではないし、最初に打つ手でもない。**

## 2. 「`pkill -INT` を送っても録画プロセスが生き続け、尺が後から伸びる」

### そう信じられていた理由

録画停止のつもりで `pkill -f recordVideo` を撃った後、`ffprobe` で尺を読むたびに
`duration` が伸びていた。「SIGINT を無視して録画し続けている」と読んだ。

### 実験で分かったこと(track2 §A)

`xcrun simctl help io` の指示どおりの作法 —— **stderr に `Recording started` が出るのを待って
録画開始とみなす → `pkill -f` ではなく実 PID に SIGINT → プロセスの exit を実際に待つ** ——
を実装したところ:

- 無操作 15 秒の録画: SIGINT から **0.013 秒で exit**。その後 25 秒間隔で5回読み直しても
  `duration` は微動だにしなかった。
- 20 タップ入りの録画: exit 後 8 秒待って読み直しても `duration=24.323333` のまま安定。

**「停止後に尺が伸びる」症状は、正しい作法では再現しなかった。**
元の観測は「exit を待たずに次のコマンドへ進み、まだ書き込み中のファイルを読んでいた」
だけだった可能性が高い(実測に基づく強い推論)。

### 派生して分かった一般的な罠

start と stop を**別プロセス呼び出し**に分ける録画スクリプトでは、bash 組み込みの
`wait $pid` が**効かない**(自分の子プロセスではないので即座に失敗して何も待たない)。
これを踏むと停止直後に `moov atom not found`(トレーラ未書き込み)の壊れた mp4 ができる。
**`kill -0 $pid` のポーリングで exit を確認すること。**(track2 §C で実際に踏んで直した)

## 3. 「`frame:{0,0,0,0}` の要素1個だけが返る = AX/HID が壊れた」

### そう信じられていた理由

`idb ui describe-all` が

```json
[{"AXFrame":"{{0, 0}, {0, 0}}","frame":{"y":0,"x":0,"width":0,"height":0},"AXLabel":null, ...}]
```

だけを返す一方で `xcrun simctl io screenshot` は正常に撮れ続ける、という
「Simulator は生きているのに走査だけ通らない」状態を何度も見た。**壊れた感**が強く、
実際 `shutdown`→`boot` で直ったので「AX が壊れた」という説明が定着した。

### 実験で分かったこと(FEEDBACK §2 / track1)

これは **「対象アプリが前面にいない」印**である。復旧は Simulator の再起動ではなく:

```bash
xcrun simctl launch --terminate-running-process <UDID> <bundle-id>
sleep 5   # レイアウト確定を待つ。短いと空/部分的な結果になる
idb ui describe-all --udid <UDID> --json   # → 20 要素返った(実測)
```

`shutdown`/`boot` は不要。**再起動で直ったのは「再起動の副作用でアプリを起動し直したから」**
という説明で足りる(推論だが、上の手順が単独で効くことを実測しているので蓋然性は高い)。

アプリが前面から落とされる原因として実地で確認されたもの:

- 同一デバイスへの外部 `xcodebuild test`(XCUITest)の割り込み。**アプリが強制終了され
  SpringBoard に戻される**(track1 で2回発生・実測)。→ SKILL.md「デバイスの所有権」参照。
- `xcrun simctl launch` 直後にまだ前面化しきっていない一瞬(track1 §5)。
  単発の `describe-all` ではなく `sim-wait.py` のポーリング経由で判定すれば自然に解消する。

## 4. 「座標は pt では効かない、px が正解」

### そう信じられていた理由(FEEDBACK §1)

入力欄を points 座標でタップしてもキーボードが出なかった。別の座標系(pixels)を試したら
たまたま直後に画面が変わったので「px が正解だった」と結論した。

### 実験で分かったこと

**`idb ui tap` は points が正しい(実測)。** `describe-all` のルート要素は
`{x:0,y:0,width:402,height:874}` を返し、その座標系での入力欄中心タップ(`181 812`)は効いた。
逆にスクショのピクセル値そのまま(`543 2436`)は**画面外として完全に無視**され何も起きなかった。

誤結論に至った原因は座標系ではなく、**2つの環境・道具の性質の合わせ技**だった:

1. **`idb ui tap` は当たっても外れても無言で exit 0** を返す(→ SKILL.md 最重要ハマりどころ 1)。
2. **ソフトキーボードが無効(ConnectHardwareKeyboard 有効)**だったので、タップが効いて
   フォーカスも入っていたのに**キーボードが出るはずがなかった**(→ SKILL.md 事前チェック)。

つまり「効いていないように見える」の正体は「観測手段が沈黙している」×「環境設定が壊れている」で、
座標系はいずれとも無関係だった。**この誤りの構造こそが、今日一番高くついた学び。**

## 5. 「idb を安定させる工夫を積めば、反復検証も idb で回せる」

明文化はされていなかったが、旧 SKILL.md の重心はここにあった(ハマりどころを潰していく構成)。

### 実験で分かったこと(FEEDBACK §6)

同じ検証(入力欄のキーボード挙動)に対して:

- idb + スクショ: **約 30 分かけて確証が得られなかった**
- XCUITest: **3本 green で合計 30 秒**

差が出た理由は道具の成熟度ではなく**判定手段の有無**にある。XCUITest には
`accessibilityIdentifier`(座標不要)・`waitForExistence(timeout:)`(固定 sleep 不要)・
`XCTAssert`(人が目で見なくてよい)が揃っている。idb にはどれも無い。

→ SKILL.md 冒頭の「棲み分け」に格上げした。**idb を否定するのではなく、
idb で探索して当たりをつけ、固まったら XCUITest へ昇格する**流れが実地では速かった。

## 6. 「`:8843` の24秒ブラックホールが探索を殺している」

### そう信じられていた理由

CalDAV の探索は複数ポートを舐めに行く。そのうち **`:8843` への接続が直結のまま
24 秒ぶら下がる**ことを実測で確認した。「初回だけこのタイムアウトに引っかかり、
トグル一覧の構築がタイムアウトで打ち切られている」——
**現象(24秒)は本物**なので、非常にもっともらしかった。

> **`:8843` と `:8443` は別物。どちらもタイプミスではない**(2026-08-01 実測で確定)。
> iOS の探索は **443 / 8443 / 8843 の3ポート**を並行して舐める。3つの性格が違う:
>
> | ポート | 実測した挙動 |
> |---|---|
> | `:443` | 正規。応答する |
> | `:8443` | **Cloudflare(workers.dev)が応答してしまう。** これが §10 の「二重チェーン」仮説の対象。`curl -X OPTIONS https://<host>:8443/dav/` が 204 を返す |
> | `:8843` | **誰も応答しない。** `nc` で 24 秒待っても接続が確立しない = 本項のブラックホール |
>
> つまり §6(このセクション)は `:8843`、§10 は `:8443` の話であり、
> **両方とも実在する別々の現象で、両方とも否定された**。

### 実験で分かったこと

**`:8843` に言及するログ行は失敗時 18 行・成功時 18 行で同数(実測)。**
失敗する1回目にだけ余計に待たされているわけではない。
**discriminator(2つの試行を分けるもの)ではなかった。**

> ※ 数え方の注意: この「18」は
> `grep -oE ":8843" <デバイスログ> | uniq -c` で得た**ログ行数**であって、
> 「18 回プローブした」ではない(1回の接続試行が複数行を吐く)。
> `state-provisioning.md` §4 の「サーバーに届いた HTTP リクエスト6件」は
> **Worker 側で数えた HTTP レベルの実数**で、層も数え方も違う。
> 比較に使ってよいのは **「両試行で同数」という relative な事実**だけで、
> 18 と 6 を突き合わせて絶対数を論じてはいけない。

### 教訓

**「本物の異常」と「今調べている症状の原因」は別物。**
24 秒のブラックホールは実在するし、いつか別の問題を起こすかもしれないが、
**この症状の犯人ではなかった。** 異常を見つけると、それが探している原因だと思いたくなる。

## 7. 「Proxyman の MITM 証明書が原因」

### そう信じられていた理由

検証中に「**サーバの識別情報を検証できません**」ダイアログが実際に出た。
Proxyman が有効で、新品 Simulator はそのルート CA を信頼していない。
**因果として完全に正しい**(→ SKILL.md 事前チェック 4 に正式な記述として採用した)。

### 実験で分かったこと

```bash
xcrun simctl keychain <UDID> add-root-cert ".../proxyman-ca.pem"
```

で **CA を入れた端末でも、トグル一覧が空になる症状は再現した。**
証明書ダイアログの原因ではあったが、**主症状の原因ではない。別個の罠だった。**

### 教訓

**環境要因を潰すのは正しい。潰した後に症状が残ったら、素直に別の原因を探す。**
「1つ環境要因を見つけた」ことに満足して、それを結論にしない。
なおこの一件は「**キャプチャに使おうとした道具が、そのまま交絡因子になった**」という
一段皮肉な形をしている。ネットワーク検証でプロキシを立てるのは自然な最初の一手なので、
次に誰かが必ず踏む。

## 8. 「トグル一覧が出た = calendar-home の PROPFIND に到達した証拠」

### そう信じられていた理由

「カレンダー/リマインダー」のトグルは **サーバー上のコレクションの内訳**を見せる UI に見える。
だとすれば、それを描くには `PROPFIND {principal}` → `PROPFIND {calendar-home}` まで
到達している必要がある。**「トグルが出ない = calendar-home に届いていない」**という
読みは、CalDAV を知っている人ほど自然に立つ。

### 実験で分かったこと

**両試行とも `PROPFIND {principal}` も `PROPFIND {calendar-home}` も送っていない(実測)。**
サーバーに届いていたのは `.well-known/caldav` → `/dav/` → `OPTIONS {principal}` の
**6リクエストだけ**。成功した2回目ですら、コレクションを一切問い合わせていない。

→ **トグルは「サーバー検証 OK」の印**であって、コレクション一覧の反映ではない。
実際のカレンダー同期(PROPFIND / REPORT)は**アカウント保存後**に始まる。

### 教訓

**UI の意味をプロトコルから推測しない。** 「この画面を描くにはこの情報が要るはずだ」は
実装の都合を無視した推測。**パケットを見れば5分で否定できる**話だった。

## 9. 🔴 「失敗する1回目だけ5周リトライしている(15件)」 — **集計ミス**

### そう信じられていた理由

ログを数えたら **1回目は 15 件・2回目は 6 件**。差は歴然で、
「1回目だけ何かに失敗して5周リトライしている」という決定的な証拠に見えた。
**ここから「リトライの果てにタイムアウトしてトグル構築が打ち切られる」という
物語を組み上げてしまった。**

### 実験で分かったこと

**15 件のうち 9 件は、別端末のログが混ざっていた。**
時刻順に並べ直すと、**両試行とも 6 件で、内容もバイト単位で同一。**
差分は最初から**存在しなかった。**

### 何が起きていたか

このラウンドでは**複数の Simulator を並行して動かしていた**(新品端末を次々に作って
対照実験を回していたため)。その状態でログを1本にまとめて採ったので、
**別端末の accountsd のログが同じファイルに流れ込んだ。**

### 教訓(SKILL.md「診断の規律」4 に格上げした)

> **複数端末を並行して動かすときは、ログを端末ごとに分けて採る。
> 混ぜると「存在しない差分」が見え、そこから誤った因果が組み上がる。**

- `xcrun simctl spawn <UDID> log ...` のように **UDID で採取先を固定する**。
  ホスト側で `log stream` を流すと全 Booted 端末が混ざる。
- 出力ファイルも **端末ごとに分ける**(`~/tmp-sim/log-<UDID>.txt`)。
- **これは道具のせいではなく、完全に自分の手順のミス。** だからこそ再発する。
  §1〜§5 の誤診が「筋の通った推論を検証せずに信じた」型なのに対し、これは
  **観測データそのものが汚染されていた**型で、より根が深い(推論の質では防げない)。

## 10. 「443 と 8443 の二重チェーンが原因。8443 に応答しない入口なら直る」

### そう信じられていた理由

探索が **443 と 8443 の2経路**を舐めており、自作サーバー(Cloudflare Workers)は
**どちらのポートでも応答してしまう**。「2本のチェーンが並行して走り、
どちらを採るかの解決に失敗している」と読んだ。
**検証しやすい予測**(8443 に応答しない入口なら直るはず)が立つのも魅力だった。

### 実験で分かったこと

**Cloud Run(`:8443` は無応答)を入口にしても、症状は再現した(実測)。**
さらに**完全に無関係な他社 CalDAV サーバー(Vikunja のデモ)でも再現**。
→ 「サーバー側のポート構成」という軸そのものが無関係だった。

### 教訓

**他人のサーバーで再現するかを試すのが、いちばん安いサーバー無関係性の証明。**
自作サーバーを疑っている間は、どうしても「自分の実装の粗」を探しに行ってしまう。
**Vikunja のデモで再現した瞬間に、探索範囲が一気に iOS 側へ絞れた。**
CalDAV に限らず、**第三者の実装を1つ用意しておくと切り分けが速い。**

## 11. 「リマインダー App を温めれば、データクラス所有者のコールドスタートに間に合う」

### そう信じられていた理由

**成功時にだけ `com.apple.accounts.dom` が remindd を起動している**という観測があった
(5/5 一致・実測。これ自体は本物)。ここから
「1回目は remindd のコールドスタートが間に合わずトグルを答えられない」と読み、
**「事前にリマインダー/カレンダー App を起動して温めておけば直る」**という
検証しやすい予測を立てた。

### 実験で分かったこと

**温めても再現した(実測)。** アプリを前面で起動しても、
**accountsd 側のデータクラス所有者の解決は温まらない。**

### 補足(まだ生きている観測)

- **`com.apple.accounts.dom` が remindd を起動するのは成功時だけ** という観測は
  **否定されていない**(相関としては 5/5)。否定されたのは
  **「App を起動すれば同じ状態が作れる」という回避策の方**。
- 「日本の祝日」も同様に無力だった。あれは **`HolidayCalDaemonAccount` という
  システム管理のデーモンアカウント**で、ユーザー追加アカウントとして数えられない(実測)。

### 教訓

**「相関のある観測」から「その状態を人工的に作る手段」を導くとき、
その手段が本当に同じ状態を作るのかは別途の証明が要る。**
ユーザーが見る「アプリが起動している」と、accountsd が見る「所有者が解決済み」は別の状態だった。

# 第3ラウンド(2026-08-01)— アカウント投入の決着で外した仮説

第2ラウンドの結論を踏まえて「まっさらから CalDAV アカウント入り端末を最小コストで作る」を
決着させに行ったラウンド。**成果側**(`webcal://` 前置きで初回から通る / clone が 16.7 秒 0タップ)は

## 12. 「`.mobileconfig` が空振りしたのは端末が新品(未ウォームアップ)だったから」

### そう信じられていた理由

第2ラウンドで**2つの本物の発見**が同時に手に入った:

- (A) `.mobileconfig` の CalDAV ペイロードは、インストール完了まで到達しても
  `Accounts3.sqlite` に行を作らない(§3・実測)。
- (B) **まっさらな端末ではユーザー追加アカウントがゼロなので、CalDAV の初回追加が失敗する**
  (§4・実測)。「端末内キャッシュが無いと、アカウント成立に必要な解決ができない」という筋。

そして **`.mobileconfig` を試した端末は、どちらもまっさらな新品だった。**
ここで「(A) は (B) の一例なのではないか」——
**未解決の問題 (A) を、同日に判明した本物のメカニズム (B) で説明できる**という
非常に魅力的な統合仮説が立った。しかも **検証方法が簡単**(温かい端末に同じ
プロファイルを流すだけ)という点まで揃っていた。

**第2ラウンド時点では「推論(未検証)」と明示して書いた。** そこは規律どおりだった。
問題は、**この筋の良さが「たぶん当たり」という空気を作っていた**こと。

### 実験で否定した(第3ラウンド・✅実測)

**実験1 — 温かい端末に流す**(仮説が直接予測すること):

対象は **CalDAV アカウントが1つ成立済み + 照会カレンダーもある**端末(§4 の意味で十分に温かい)。
プロファイルは実サーバー(既存アカウントとは別ホスト)。

| | 実測 |
|---|---|
| インストール UI | ✅「インストール完了」まで到達 |
| `Accounts3.sqlite`(前) | 4 行 |
| `Accounts3.sqlite`(後・+20 秒待ち込み) | **4 行のまま。増えない** |

→ **仮説の予測(温かければ行が立つ)は外れた。**

**実験2 — 認証すら不要なペイロードでも作られない**(仮説を超えて否定を強めた):

`com.apple.subscribedcalendar.account` **だけ**のプロファイルを新品端末へ。
照会カレンダーはサーバー認証も要らない、最も単純なアカウントペイロード。

| | 実測 |
|---|---|
| インストール UI | ✅「インストール完了」。内容欄に「照会カレンダー」と正しく表示 |
| `Accounts3.sqlite` | **2 行のまま。増えない** |

**同じ購読を `webcal://` から手で入れれば行は立つ。**
→ ペイロードの記述ミスでも、認証の問題でも、温度の問題でもない。

**実験3 — 配送経路は生きていることの確認**(「そもそも届いていない」を潰す):

`ProfileTruth.plist` / `PayloadManifest.plist` / `MCProfileEvents.plist` のいずれにも
プロファイルが正しく登録されていた。**配送は成功しているのにペイロードが効いていない。**

### 更新後の結論

> **iOS Simulator では、アカウント系ペイロード全般がアカウントを作らない。
> 端末の温度とは無関係で、CalDAV 固有ですらない。**(→ `state-provisioning.md` §3)

🔶 残る推論: `profiled` → `accountsd` のアカウント作成経路が Simulator では結線されていない。
❓ 未検証: 非アカウント系(Wi-Fi・証明書・制限)のペイロードが効くかどうか。

### 教訓

**新しい型の誤診がここで1つ増えた。**
§1〜§5 は「筋の通った推論を検証せずに信じた」型、§9 は「観測データが汚染されていた」型。
これは3つ目 —— **「本物の発見を、別の未解決問題の説明に流用した」型。**

1. **同じ日に見つけた本物のメカニズムは、手近な説明装置として過剰に使われる。**
   (B) は実測に裏打ちされた真の発見だったので、それを土台にした (A) の説明まで
   **実測の信頼性を借りてしまった**。**土台が実測でも、そこから伸ばした推論は推論のまま。**
2. **「未解決の問題が2つあり、片方が解けた」とき、もう片方も同じ原因だと思いたくなる。**
   §6 の教訓(「本物の異常」と「今調べている症状の原因」は別物)の**変奏**。
   同じ罠に、別の入口から落ちている。
3. ✅ **助かったのは「推論(未検証)」と明示して書いてあったこと。**
   だから第3ラウンドで**まずそれを検証する**という手順が組めた。
   事実として書いていたら、その上に手順を積んでいた。**ヘッジの明示は、後で回収するための投資。**
4. **否定するときは、仮説の予測(実験1)だけでなく、結論を強くする実験(実験2)も撃つ。**
   実験1だけなら「温度以外の何かが足りない」で終わったが、実験2があるので
   **「アカウント系ペイロード全般」**まで言い切れた。**否定は、次の人の探索範囲を狭める形で残す。**

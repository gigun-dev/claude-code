# コメント方針

**必要十分に書く。多いほど良いではない。**
(旧: 「コードと同量レベルでベッタベタに」。2026-09-04 に撤回。cf-fireboard で src の 45% が
コメントになり、1 ファイル読むたびに 10 万 token 級を通り、積層した旧文が次の書き手の手本になって
増え続けた。経緯は `references/comment-culture-source.md`)

1. **ファイル冒頭**: 何を守るか / 何の事故を止めるか / なぜここに在るか。短く。
2. **行のコメント**: その行の**理由**だけ。何をしているかはコードが言う。
3. **ボツ案**は、誰かがまた提案しそうなものだけ 1 行。経緯の語り(最初は X、次に Y)は書かない。
4. **訂正は置き換える。** 旧文は 1 行に畳む: `(旧: 〜。YYYY-MM-DD に誤りと判明 → 理由)`。
   積層(訂正の上に訂正)はしない。全文は git にある。
5. **観測値は `[実測 YYYY-MM-DD <条件>]`。** 条件まで書く。
6. **既存の密度に合わせない。** ツールの既定は「周囲のコメント密度に合わせる」なので、肥大化した
   ファイルを触るとそのまま増える。触った箇所は上の基準で書き、周囲が多くても倣わない。
7. **記号(絵文字・警告マーク)は使わない。** 強調は文で言う。全部を強調すると強調が消える。
8. **編集する前に対象ファイルを Read する。** subagent への指示にもこの 1 行を入れる。
9. **コメント比率を目標にしない。** 必要十分は TPO なので、割合では判定できない —— 型定義だけの
   ファイルは各欄 1 行の JSDoc を残すだけで 40% を超えるし、逆に低い比率は「理由が書かれていない」
   ことも意味する。比率は**どのファイルを見に行くかを決める計器**として使う(依頼者への報告は
   結果の観測値として載せてよい)。刈り込みの完了条件は 1〜7 の各項目であって数字ではない。
   (2026-09-08 の裁定。この項が無かったため、刈り込みを委譲した先へ「25%」という
   存在しない目標を渡し、実測の記録を数字のために削らせかけた)

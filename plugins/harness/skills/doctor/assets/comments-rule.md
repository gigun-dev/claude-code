# コメント方針

必要十分に書く。多いほど良いではない。
(旧: 「コードと同量レベルでベッタベタに」。2026-09-04 に撤回。cf-fireboard で src の 45% が
コメントになり、1 ファイル読むたびに 10 万 token 級を通り、積層した旧文が次の書き手の手本になって
増え続けた。経緯は `references/comment-culture-source.md`)

この文書は強調記号を使わない。規則は最も繰り返し読まれる手本なので、ここで強調していれば
強調の癖がコメントへ写る(2026-09-08 の裁定)。要点は文の順序と番号で示す。

1. ファイル冒頭: 何を守るか / 何の事故を止めるか / なぜここに在るか。短く。
2. 行のコメント: その行の理由だけ。何をしているかはコードが言う。
3. ボツ案は、誰かがまた提案しそうなものだけ 1 行。経緯の語り(最初は X、次に Y)は書かない。
4. 訂正は置き換える。旧文は 1 行に畳む: `(旧: 〜。YYYY-MM-DD に誤りと判明 → 理由)`。
   積層(訂正の上に訂正)はしない。全文は git にある。
5. 観測値は `[実測 YYYY-MM-DD <条件>]` の形で書く。条件まで書く。
6. 既存の密度に合わせない。ツールの既定は「周囲のコメント密度に合わせる」なので、肥大化した
   ファイルを触るとそのまま増える。触った箇所は上の基準で書き、周囲が多くても倣わない。
7. 絵文字・絵記号を使わない。要点・注意・禁止は文で言う。判定は Unicode の
   `Extended_Pictographic`(記号を数個列挙する規則にしないこと。それ以外が素通りする)。
   - `**` の強調も使わない。コメントは Markdown として描かれないので読む側には字が増えるだけで、
     全部を強調すれば強調は消える。規則文・CLAUDE.md・正典のテンプレも同じ(手本になるから)。
     人が読む README や docs は対象外。
   - 対象外は、記号としての意味を担うもの(`↔` の対比、`──▶` の図の矢印)、挙動として在るもの
     (検査の期待値・入力値)、`2 ** 3` のべき乗、そしてモデルに渡る文(執行されている契約の
     見本がありうる。変更は実測での再検証が要る)。
8. 編集する前に対象ファイルを Read する。subagent への指示にもこの 1 行を入れる。
9. コメント比率を目標にしない。必要十分は TPO なので、割合では判定できない —— 型定義だけの
   ファイルは各欄 1 行の JSDoc を残すだけで 40% を超えるし、逆に低い比率は「理由が書かれていない」
   ことも意味する。比率は、どのファイルを見に行くかを決める計器として使う(依頼者への報告は
   結果の観測値として載せてよい)。刈り込みの完了条件は 1〜8 の各項目であって数字ではない。
   (2026-09-08 の裁定。この項が無かったため、刈り込みを委譲した先へ「25%」という
   存在しない目標を渡し、実測の記録を数字のために削らせかけた)

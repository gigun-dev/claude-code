> **いつ書くか** — 「作業の区切りごと」は毎回その場で判断を強いるので、**条件を先に決めておく**
> (Google SRE の "define postmortem criteria **before** an incident occurs" と同じ形。
> 事後に基準を作ると、書かない理由がいくらでも立つ)。次のどれかに当たったら書く:
>
> 1. **判断をした** — 選択肢が2つ以上あり、片方を選んだ。**却下した案と却下理由も書く**
>    (採用案だけ残すと、次に同じ検討を最初からやり直すことになる)
> 2. **想定が外れた** — 見込みと実測 / 実挙動が違った。**数値があれば数値で**
> 3. **手で介入して直した** — 自動で通らず、人が回避策を入れた
> 4. **想定より時間がかかった** — 詰まった箇所と、何が効いて抜けたか
> 5. **やり直しの効かない変更をした** — 破壊的変更・外部への公開・データ移行
> 6. **過去ログを読んだ** — そのとき足りなかった情報を、その場で足す(下の「いつ読むか」)
>
> どれにも当たらないと判断したときも、**1行だけ残す**: `- (記録不要: 定型作業のみ)`。
> 黙って抜けるのと「書かないと決めた」の区別が付き、かつ摩擦は1行分で済む
> (Kubernetes が `/release-note-none` を必須にしているのと同じ設計)。
>
> **その場で書く(contemporaneous)。** 後からまとめて書くと、思い出せるものだけに縮む。
> 記録すべきは「何をなぜ決めたか、**その時点で判断に影響したものは何か**」(PIC/S の
> 記録要件の定義)。**判断に影響した材料**は、結論と違って翌日には失われている。
>
> **見出し**: `## YYYY-MM-DD 一行タイトル`。同じ日に複数回書くなら見出しを複数立てる
> (1見出し = 1つの区切り)。**日付だけの見出しにしない** —— 索引と拾い読みが効かなくなる。
> 見出しは高くつかない: 実測(caldav)で 1,424 行に対し見出し 50 本 = 本文の 2.8%。
> **`## ` はエントリ専用**。運用ルールや補足に使わない(索引が汚れる)。
>
> **既存の見出しと本文は書き換えない。** 訂正は**新しいエントリ**で行う。どうしても本文に
> 触るなら取り消し線 + `> **YYYY-MM-DD 訂正:**` を添えて、消さずに残す。追記専用は
> 「本当に書き換えていないこと」を git 差分(+N -0)で検証できる唯一の担保。
>
> **いつ読むか** — 全文ロードはしない。次のどれかに当たったときだけ、索引から拾って読む:
>
> 1. **現在の設計の理由が next-directions に書いていない** — 変更する前に「なぜこうなって
>    いるか」を知りたいとき(盲目的に受け入れる / 盲目的に変える の二択を避ける)
> 2. **同じ判断をもう一度しようとしている** — 過去に検討して却下した案かもしれない
> 3. **同じ症状を再度踏んだ** — 前回どう抜けたか
> 4. **他人(未来の自分)に経緯を説明する必要が出た**
>
> **読んだら、その場で足りなかったことを追記する**(= 書く条件6)。更新の発火条件を
> 「気づいたとき」ではなく**その文書が実際に使われた瞬間**に固定する(SRE Workbook:
> on-call は**対応する page が鳴ったときに** playbook を更新する)。「気づいたとき」は
> 発火しない条件の言い換えでしかない。
>
> **git との使い分け**: 「**この行が**なぜこうなったか」は `git blame`(コミット単位)。
> 「**なぜこの方針を選び、何を却下したか**」はここ(判断単位)。却下案は差分に残らないので、
> git からは原理的に復元できない —— そこがこのファイルの存在理由。
>
> **却下・見送りには `R-n` を振る**(バッククォート囲み。着手順の `H-n` と同じ記法)。
> 書式は ``- `R-n` **却下: <一行タイトル>** — <理由>``(見送りなら `見送り:`)。**既存の
> 文章は書き換えず、ID とラベルを前置するだけ。**採番は**時系列で追記専用** —— 欠番も
> 再利用もしない。理由には**判断の根拠**(一次資料 URL / issue 番号 / 実測値)を添える。
> ⚠️ **ただし過去分は遡らない。**後から入れたルールを遡及させようとすると、達成できずに
> 規約ごと死ぬ(PEP は Rejected 131 本中 `Resolution:` を持つのが 42 本だけ)。
> ID を振る理由は**引けるようにするため**だけ —— Rust RFC 3137 が6年前に closed した PR の
> 個別コメントを今でも引けるのは URL が安定 ID だったからで、ID の無い段落は引けない。
> `R-n` を含む行は下の**却下索引**へ自動で集まる(日付を知らなくても判断から辿れる)。
>
> **ローテーション**: 年単位で切る。年が変わったら本体を `docs/log/YYYY.md`
> (コンポーネント別なら `docs/<component>/log/YYYY.md`)へ移し、本体は新しい年から始める。
> **ただし本体が 1,500 行を超えたら年の途中でも切り出す**(暴走ガード)。切り出した
> ファイルの**末尾には次のファイルへのリンクを置く**(前から後ろへ辿れるようにする)。
> **アーカイブを1本に押し込まない** —— Angular の CHANGELOG_ARCHIVE.md は 1.1MB に達し、
> アーカイブ自体が閲覧不能になった。現行の区切りは本体に残し、**1世代前が確定した時点で**
> 切り出す(進行中のものを動かすと、追記先が2箇所になって必ず片方が腐る)。
> 1,500 行という数字は**バイトサイズの限界ではなく全文ロードの費用**から来ている:
> 実測(2026-08-07)で caldav が 1,424 行 / 146KB とすぐ手前におり、GitHub の描画実効限界
> 0.5MB に対してはまだ 1/3.4 —— **バイトはまだ問題になっていない**。
> ⚠️ **閾値を上げて警告を消すのは禁止。下げ直すのは可**(ハーネス既存のラチェット防止規約と
> 同じ。上げ方向を許すと検知がラチェット式に静かに死ぬ)。
>
> **索引**(先頭のマーカー間。日付索引と却下索引の2つ)は**自動生成。手で書かない。**
> `/harness:tidy` が古さを検知し、
> `skills/tidy/scripts/log-index.sh` が書き換える。**索引は新しいものが上、本文は追記専用
> なので末尾が最新** —— この非対称は意図的で、「今どうなってる?」に索引だけで答えるため。

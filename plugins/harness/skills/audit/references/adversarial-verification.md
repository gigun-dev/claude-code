# 敵対的検証の方法(2026-08-05 取得時点の要旨)

出典: https://zenn.dev/loglass/articles/6aa18c80496ec6
(Anthropic 公式ベストプラクティスの「Adversarial verification」に基づく手法解説)

## 方法

1. **観点を分けた複数の検証エージェント**(通常3体)を並列に立てる。
   実績のある観点分割: ①実行系(成果物を実際に動かして壊す) ②仕様適合(公式ドキュメント
   等の一次情報に接地) ③設計レッドチーム(前提が壊れるシナリオを攻める)。
2. **fresh context**: 作成時の経緯・意図を渡さず、成果物だけを読ませる。
3. **課題がある前提で反証を試みさせる**。指摘には4項目を必須付加:
   指摘内容(一言) / 深刻度(高中低) / 根拠(一次情報の出典) / 確度(高中低)。
   最後に「反証できなかった点」を1〜2行(過剰指摘の抑制)。

## 裁定の原則

- **指摘 = 間違いではない。** 「ギャップを探せ」と言われた検証者は健全な成果物にも指摘を出す。
  深刻度「高」の指摘ほど一次情報(原文引用・本番実績)で潰す価値がある。
- 逆方向(手抜きの「合格」)の方が危険。「大丈夫」と言われても自分で見る。
- 同一モデルの盲点: 知識的誤りはすり抜ける。「一次情報に当たって」の接地指示で回避する。
- コストは3〜10倍。やり直しコストが高い成果物(複数リポへ配布するテンプレート等)に絞る。
- **採否を決めるのは人間。AI の指摘は判断材料。**

## 実績(2026-08-05、harness v0.1.0 → v0.2.0)

3体・計21指摘 → 採用14(フェイルオープン修正・書式統一・鮮度検知の新設等)/
偽陽性2(いずれも深刻度「高」— 公式 doc 原文引用と本番実績で棄却)/
再裁定1(Codex 配線は実在した — 検証者ではなくユーザーの追加情報で判明)。

# ADR Format(軽量。costs を明示する)

## 評価軸にした研究

2026-09-25 の実測: 9 個の実在するリポジトリから 249 件の ADR を採り、語数の
分布を見た。最も軽い部類(adr-tools 系)でも中央値は約 160 語で、このプラグイン
がその日の朝まで採っていた「1〜3 文」の書式(実測 ~68 語)はその corpus の
下位 10 パーセンタイルより軽かった —— 実在する ADR の慣行から外れて軽すぎた
ということ。

調べた 249 件は例外なく consequences(決定の結果)を持っていた。これは複数の
文献と一致する:

- Michael Nygard(2011, ADR の原典)—— "list all consequences, not just the
  positive ones."(良い結果だけでなく、悪い結果も含めて全部挙げる)
- Olaf Zimmermann の Y-statement —— 文脈・懸念(concern)・決定・捨てた案・
  重視した性質・**受け入れる欠点(accepting downside)**・根拠、という構造。
  同じ著者が「Free Lunch Coupon」(costs を書かない ADR)と「Fairy Tale」
  (良いことしか書かない ADR)を反パターンとして名指しし、Definition of
  Done として costs の明記を挙げている。
- Martin Fowler / Microsoft の ADR ガイダンス —— 検討した代替案とその却下
  理由、確信度(confidence)、見直す条件(revisit)を含めることを勧める。

このプラグインが上記と一致しないのは 1 点だけ: 差し替えられた決定をファイルに
残さない(`adr replace` がファイルごと消す。理由は下の「差し替え」節)。
costs を明示する点、文字数を機械的に縛らない点は一致させた。

## 書式

```md
# {決定の題}

Date: {YYYY-MM-DD}
Implementation: {done | pending}

{文脈。1 段落}

{決定と理由。1 段落}

{任意: 帰結。1 段落}

Accepting: {受け入れた代償}
Rejected: {捨てた案} — {捨てた理由}
Revisit: {この決定を見直す条件}
```

- **題** は 1 行目の `# ...`。
- **`Date:`** は決定した日。この 1 行だけに書く —— 本文の中に別の日付を
  置かない(それは measurements かコミットメッセージの役目。コードスパンに
  入れた識別子としての日付は除く。後述)。
- **`Implementation:`** は `done`(もう実装されている)か `pending`(まだ)の
  どちらか。省略できない —— 状態を一言で示す場が無いと、決定と実装の乖離が
  ADR を読むだけでは分からなくなる。
- **`Status:`** は省略できる。書けるのは `proposed` だけ(書かなければ
  `accepted` として扱う)。`deprecated` / `superseded` は語彙に無い ——
  差し替えられた決定はファイルごと消すので、そういう状態が存在しない。
- **本文は短い段落を最大 3 つ**(文脈・決定・理由。任意で帰結)。目安は
  120〜200 語だが `adr check` は数えない(数えて縛ると、縛った単位に長文を
  詰め込む結果になる —— 1 段落だけ・1〜3 文だけに縛った版が実際にそれで
  壊れた)。段落 4 つ以上は `adr check` が指摘する構造上の後備え(次節)で
  あって、3 つ以内なら軽いという意味ではない。長さの実際の目安は
  `adr stats` の語数で見る。
- **`Accepting: <代償>` は必須(最低 1 行)。** 受け入れた costs・トレード
  オフを書く。無い ADR は Zimmermann の言う Free Lunch Coupon(costs 抜き)
  で、`adr check` が指摘する。
- **`Rejected: <案> — <理由>`** は任意・複数可。理由(` — `以降)は必須 ——
  無いと `adr check` が指摘する。
- **`Revisit: <条件>`** は任意。この決定を見直す条件(例: 利用者数が増えた
  ら、依存先が別の解を提供したら)。Fowler / Microsoft のガイダンスに沿う。
- **`Replaces: <古い番号>`** は任意・複数可。`adr replace` が書く(手で
  書かない)。この ADR が置き換えた古い番号を並べる(古いファイル自体はもう
  無い)。

## 軽さの強制の仕方

文字数・語数の上限は置かない —— 数に原理的な根拠が無く、言語(日本語 / 英語)
でも 1 語あたりの情報量が違う。軽さは**形と costs の有無**で強制する:
`adr check` は次を指摘する。

- `##` 以上の見出し
- 箇条書き・番号付きリスト
- 表(`|`)
- コードフェンス(` ``` `)
- 引用(`>`)
- 本文の段落が 4 つ以上
- `Accepting:` が 1 行も無い
- `Rejected:` の行に理由(` — `)が無い

見出しや箇条書きが要る決定は、実際には複数の決定か、決定というより手順書
(それは docs や README の役目)。

`adr stats` は check とは別に、ファイルごとの文字数(`wc -m` 相当)・語数
(`wc -w` 相当。空白区切りなので、分かち書きしない言語では過小に出る)・
段落数・文の数・最長の文の文字数を、文字数の多い順に報告する(合否は判定
しない。常に 0 で終わる)。目安の 120〜200 語を check が縛らない分、
`adr check` の後に `adr stats` を走らせ、語数や文が多い/長いものを split の
候補として扱う。書いた直後に限らず、軽さが安定するまでは定期的に見る。
書きすぎ(関係ない背景や手順まで書く「Mega-ADR」)にも、削りすぎ(costs や
理由を削って前提ごと消す過剰圧縮)にも寄らない —— どちらも実際にこの
プラグインで起きた(2026-09-25 の同日に両方)。

## 文単位の関門(構造だけでは軽くならない)

段落 3 つ・`Accepting:` あり、という構造の条件は `adr check` が機械的に見られる
範囲でしかない。それでも中に「覆すのが安いサブ決定」がいくつも束ねられて
いれば、軽い ADR ではない(check は通るが実質は重い)。この線引きは構造では
検査できないので、書く/レビューする側が**文ごとに**許可テストを掛ける: その
文は、この ADR が記録する**1 つの覆しにくい決定**について書かれているか。

- そうでない文 —— 実装の詳細やそれ自体は覆すのが安いサブ決定 —— は ADR に
  残さない。行き先は、その実装を行うコードのそばのコメントか、コミット
  メッセージ。
- 許可テストを適用した結果、本文の全文がそのどちらかへ移ってしまう(=
  覆しにくい決定について書かれた文が 1 つも残らない)なら、その ADR 自体が
  三重関門(下記「いつ書くか」)を満たしていなかったということ。ADR ごと
  消し、理由はコードコメントへ移す。

## 内容の線引き

ADR の本文に置かないもの(`adr check` が指摘する):

- 測定値・実測ログへの参照(`[実測 ...]`)。行き先は `measurements/*.jsonl`。
- テスト名への参照(`[検査: ...]`)。行き先はコミットメッセージかテストその
  もの。
- todo の id 参照(`id:0123`)。決定から生じた作業は todo.txt の 1 行にし、
  そちらから `see:docs/adr/NNNN-slug.md` で ADR を指す(逆向きの矢印は張らない)。
- `Date:` の行以外に置かれた日付。経緯は commit メッセージか measurements
  に書く。ADR が持つ日付は「決定した日」の 1 つだけでよい。ただし
  バッククォートのコードスパン(`` `2026-07-28` ``)の中は見ない ——
  仕様やプロトコルがバージョンを日付そのもので識別する場合(例: MCP)が
  あり、それは経緯ではなく値なので、コードスパンに入れて書けば指摘しない。

## 採番

既存ファイルの番号の最大値 + 1。4 桁ゼロ詰め。欠番は埋めない —— 番号は採ったら
永久で、`Replaces:` が名指しする(= 既に消えた)番号も含めて max を取る
(`adr new` が両方を見る)。

## 差し替え(replace)

決定が変わったら、新しい ADR を `adr new` で書き、`adr replace <古い> <新しい>`
を実行する。これが行うのは 2 つ: 新しい方に `Replaces: <古い番号>` を書き足す
こと、古い方のファイルを消すこと(git 管理下なら `git rm`)。

**古いファイルを deprecated / superseded のまま残さない。** 理由は、エージェント
は自分のコンテキストに載っているものを「今も有効な情報」として扱う傾向がある
—— 新旧の矛盾する情報を同時に渡されたときにモデルがどちらを選ぶかを調べた
研究(ClashEval, 2024)は、この種の食い違いが読み手を誤らせることを示している。
Claude Code の memory ドキュメントが「相反する指示を残さない」と勧めるのも
同じ理由。置き場(`docs/adr/` など)には**今も有効な決定だけ**を残し、消した
決定は git の履歴が持つ(`git log -- docs/adr/0001-....md` で読める)。

部分的な差し替え(決定の一部だけが変わった)は、古い ADR の残りの決定を
新しい ADR に書き直すか、古い ADR 自体を短くしてから `adr replace` する ——
**編集するか消すか、どちらかにする。差し替えた文面を置き場に残さない。**

## 受理済み ADR を編集してよい範囲

短くする(段落を削らず言い換えて縮める)ことと、`Implementation:` を
`pending` → `done` に更新することだけ。**決定そのものが変わったら、それは
このファイルの編集ではなく `adr replace` で新しい番号にする。**

## いつ書くか

書くのは次の三つが全部そろうときだけ(Nygard / Azure と同じ基準):

1. **覆すのが高い**。後から考え直す費用が大きい。
2. **文脈が無いと驚く**。将来の読み手がコードを見て「なぜこうした」と思う。
3. **本物の取引の結果**。実在する代替案があり、理由を持って片方を選んだ。

一つでも欠けたら書かない。覆すのが安いなら、そのとき覆せばよい。驚かないなら
誰も理由を尋ねない。代替案が無いなら「そうするしかなかった」以上に書くことが
無い。
